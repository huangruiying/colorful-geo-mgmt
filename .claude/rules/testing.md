# 测试规范

本文件定义通用测试原则与单元测试 / 集成测试 / E2E 分层边界。真实接口请求、日志归因、代码修复、重启回归、`.test` 报告落地见 `rules/runtime-api-test.md`。

---

# 1. 测试目标

测试的核心目标：

- 验证业务行为
- 防止回归问题
- 降低重构风险
- 提升修改信心
- 让代码可以稳定演进

测试不是为了凑覆盖率数字。

---

# 2. 核心原则

## 2.1 测试行为，不测试实现细节

测试应优先验证：

- 输入与输出
- 状态变化
- 业务规则
- 副作用
- 边界条件

避免把测试和内部实现强绑定。

---

## 2.2 测试名称应表达场景

测试名应尽量体现：

- 什么场景
- 触发什么动作
- 预期什么结果

推荐：

```java
shouldRejectOrderWhenInventoryNotEnough()
```

不推荐：

```java
testCreateOrder()
```

---

## 2.3 一个测试聚焦一个行为

一个测试可以有多个断言。

但这些断言应共同验证同一个行为结果。

禁止一个测试同时覆盖多个不相干场景。

---

# 3. 必须补测试的场景

以下场景必须补测试：

- 新增业务规则
- 修复缺陷
- 关键流程重构
- 边界条件处理
- 状态机修改
- 重试逻辑修改
- 缓存策略修改
- 权限逻辑修改
- 风控逻辑修改

---

## 3.1 缺陷修复必须先覆盖问题场景

修复 bug 时，测试至少应覆盖：

- 原问题如何复现
- 修复后结果是否正确
- 相邻场景是否被影响

避免只改代码，不补防回归测试。

---

# 4. 测试分层规范

## 4.1 单元测试

用于验证：

- 单个方法
- 单个类
- 单个规则
- 单个分支

要求：

- 运行快
- 定位准
- 依赖少

---

## 4.2 集成测试

用于验证：

- 模块协作
- 数据库交互
- 缓存交互
- 消息交互
- 外部接口适配

要求：

- 验证真实边界
- 覆盖关键集成路径

---

## 4.3 端到端测试

用于验证：

- 主流程是否可用
- 关键用户路径是否打通
- 系统级回归是否出现

不应用 E2E 替代单元测试和集成测试。

真实服务接口请求、日志归因、重启回归和 `.test` 报告落地不在本文件展开，执行时加载 `rules/runtime-api-test.md`。

---

# 5. 测试用例设计规范

## 5.1 至少覆盖正常路径与异常路径

核心测试应尽量覆盖：

- 正常场景
- 非法输入
- 边界值
- 空值场景
- 异常场景

---

## 5.2 测试数据应可读

测试数据应：

- 语义明确
- 尽量减少魔法值
- 避免读不懂的随机数据

推荐：

```java
int stock = 0;
int orderQuantity = 1;
```

不推荐：

```java
int a = 17;
int b = 23;
```

---

## 5.3 断言必须精确

断言应直接验证核心结果。

不推荐：

```java
assertTrue(result != null);
```

推荐：

```java
assertEquals(OrderStatus.REJECTED, result.getStatus());
```

---

# 6. 稳定性规范

## 6.1 测试必须可重复运行

测试应避免依赖：

- 随机时间
- 真实网络波动
- 共享环境脏数据
- 执行顺序偶然性

测试失败应尽量稳定可复现。

---

## 6.2 禁止脆弱测试

例如：

- 依赖 `sleep` 等待结果
- 依赖外部服务偶然可用
- 断言文案中的无关格式细节
- 断言过多不稳定中间过程

---

# 7. Mock 使用规范

Mock 应优先用于：

- 难以稳定构造的外部依赖
- 明确不属于当前测试目标的协作者
- 高成本或高副作用调用

禁止为了让测试更容易写，而把核心业务逻辑全部 mock 掉。

---

# 8. 可维护性规范

## 8.1 测试代码也要可读

测试代码应保持：

- 结构清晰
- 命名清晰
- 准备数据简洁
- 断言重点明确

测试代码不是一次性脚本。

---

## 8.2 避免重复样板

当多个测试存在重复准备逻辑时：

- 可以提取测试工厂
- 可以提取夹具方法
- 可以提取公共构造函数

但不要过度抽象到难以理解。

---

# 9. Review 检查项

Code Review 时必须检查：

- 是否覆盖关键业务行为
- 是否覆盖边界与失败场景
- 测试名是否表达场景
- 断言是否精确
- 是否存在脆弱测试
- 是否过度 mock
- 缺陷修复是否补了回归测试

---

# 10. 最终原则

优秀测试应做到：

- 失败时能快速定位问题
- 修改后能快速判断是否回归
- 读测试就能理解业务规则
- 不因测试本身制造维护负担

测试应保护代码演进。

而不是阻碍代码演进。
