# 诊断任务实施计划

日期：2026-10-13。状态：用户已确认实施，第一版表结构、ORM、任务创建、后台执行、查询和页面已完成。实际实现见 [诊断任务功能与接口](诊断任务功能与接口.md)，验证见 [回归报告](../.test/诊断任务功能回归报告.md)。

## 目标与使用流程

用户在「诊断任务」页面选择一个已保存的诊断方案，确认本轮采样规模后发起执行。任务在后台调用方案指定的模型渠道，逐次保存回答；用户可以关闭页面，之后回来查看进度、回答、引用和失败原因。

例如：20 个问题 × 2 个渠道 × 重复 3 次 = 120 次独立请求。重复采样不携带前一次回答，也不向被测模型注入项目资料；项目资料仅保存在快照中，供后续分析使用。

## 已有基础与本轮边界

已核对源码和设计文档：

- 诊断方案已有项目、问题、指定渠道和重复次数。
- `geo_diagnosis_plan_exec_record`、`geo_diagnosis_plan_exec_record_result` 及实体、DAO 已存在；本轮已核对本地 MySQL，两表快照、唯一键和约束齐全，018 已增加创建请求标识与唯一索引，实体及 001/011 同步。
- `diagnosis-tasks.html` 目前是功能规划占位页。
- 当前 `LLMQueryRequest` 按渠道编码、模型筛选，再按优先级选一条配置，尚无按方案渠道 ID 精确调用的入口。
- 当前 `LLMResponse` 只有正文和引用，尚不能填充执行结果表中的实际模型、用量、结束原因和原始响应。

第一版包括：手动发起、异步执行、状态与进度查询、任务列表、采样结果分页和回答详情。补充任务 Controller、Business、执行 Service 和必要的后台执行组件，沿用现有模型策略；不引入消息队列或通用工作流框架。

定时执行、取消任务、失败样本重试、品牌评分和诊断报告放到后续阶段。第一版失败后可再次发起完整新任务，保留旧任务，页面明确这是重新执行全部采样。现有页面的“重试失败样本”规划文案相应调整为后续能力。

## 第一阶段：创建任务与冻结配置

1. 页面提供「发起诊断」，选择方案后显示项目、问题数、渠道、重复次数和总调用次数。最终采样规模以服务端创建结果为准。
2. 服务端校验项目和方案存在、问题合法、渠道已启用、策略 Bean 已注册、远程渠道密钥存在。发现无效配置时拒绝创建，指出需要修正的配置。
3. 在短事务内读取一致的方案配置，冻结项目资料、方案、完整问题及渠道非敏感配置，并创建全部待执行结果。任一步失败整体回滚。
4. 每条结果由“任务 ID＋问题序号＋渠道 ID＋重复序号”唯一确定，沿用现有唯一键。
5. 创建请求带本次提交的唯一标识，服务端持久化去重；同一次点击的重复请求返回同一任务，不重复计费。标识相同而方案不同则拒绝。执行记录的 `request_id`、唯一索引、接口校验与并发冲突事务外回读均已实现。

任务内的问题、模型、策略、地址和生成参数按创建时快照执行；方案后续编辑不影响已有任务。API Key 不进入快照或接口，执行时按渠道 ID 读取当前凭据。渠道被删除、停用或非敏感配置发生变化时，未开始的对应样本明确失败，要求创建新任务，避免静默使用变化后的测试配置。

第一版每个采样开始前进行渠道检查；密钥轮换不改变历史快照。调用开始后发生的配置修改不撤回已经发出的请求。

## 第二阶段：后台执行与模型结果保存

### 执行方式

采用单实例、数据库待执行记录驱动的后台执行方式。服务端创建任务后立即返回，不让浏览器请求等待全部模型调用完成。

- 第一版默认一个任务运行、任务内串行采样，其余排队；使用有界执行资源，不按采样数量创建线程。
- 后台周期检查待执行任务，按创建顺序处理；通过条件更新领取任务和结果，避免同一实例重复执行。
- 外部 HTTP 调用放在事务之外；领取结果、保存回答分别使用短事务。
- 单次失败继续处理其余采样，不更换渠道，不用 Mock 自动降级，不自动重发外部请求。
- 日志只记录任务/结果 ID、渠道、状态、耗时及安全错误分类，不写凭据或完整问题和回答。

### 模型调用改动

在现有 `LLMClient` 和路由器中补充指定渠道执行入口，保留普通查询现有优先级选择行为。任务调用必须命中方案保存的渠道 ID，不能使用默认渠道代替。

复用现有 Spring 策略 Map、协议模板和统一 HTTP 配置。扩展统一模型响应以携带实际模型、Token 用量、结束原因及响应体，同时保留现有正文和引用读取方式。厂商未返回的字段保存为空，不根据请求配置伪造“实际模型”或用量。

回答正文与结构化引用分别保存。成功且无引用保存空数组；不从正文猜测引用。原始响应仅限响应体，并做敏感字段处理；不得保存认证头、请求密钥或远程异常原文。列表不返回大段原始响应，详情按需查询。

### 状态与异常

| 层级 | 状态与含义 |
|---|---|
| 任务 | 待执行 → 执行中 → 全部成功 / 部分失败 / 全部失败 |
| 采样 | 待执行 → 执行中 → 成功 / 失败 |

计划、成功、失败、待执行和执行中数量从结果表聚合，不重复保存计数。只有全部样本结束后才汇总任务终态。

服务重启时：尚未开始的排队任务可继续检查并执行；此前正在运行的任务终止为失败或部分失败，其未完成结果标明“服务中断，结果未确认”或“未执行”。不自动重发状态不确定的调用，避免重复计费。第一版仅支持单实例，启动恢复不得用于多实例部署；后续多实例需另行设计租约和恢复归属。

如果模型已返回但结果落库失败，停止该任务的后续调用并保留已落库回答。数据库恢复后将该任务未完成结果标记为失败；不得因落库失败自动再次调用模型。后台循环应隔离任务异常，避免一个任务出错停止整个执行组件。

## 第三阶段：诊断任务页面与接口

沿用管理后台现有页面布局和弹窗交互，不新增侧边流程。

| 页面操作 | 内容 |
|---|---|
| 发起诊断 | 选择方案，确认项目、渠道和采样规模，提交一次任务 |
| 任务列表 | 方案、项目、创建时间、状态、进度及查看入口；支持分页与方案/状态筛选 |
| 查看任务 | 冻结的配置、总体和各渠道统计、采样结果分页 |
| 查看回答 | 问题、渠道、重复序号、正文、引用、实际模型、用量、耗时及安全失败原因 |

执行中的详情定期刷新进度，结束或关闭详情后停止刷新。页面重载不会重新创建任务；创建失败保留选择并显示原因。

建议接口：

| 方法与路径 | 用途 |
|---|---|
| `POST /diagnosis-tasks` | 按方案 ID 和提交标识创建任务，返回任务 ID、状态和采样数 |
| `GET /diagnosis-tasks` | 分页筛选任务 |
| `GET /diagnosis-tasks/{id}` | 查询快照、状态及聚合进度 |
| `GET /diagnosis-tasks/{id}/results` | 按状态、渠道分页查询采样结果 |
| `GET /diagnosis-tasks/{id}/results/{resultId}` | 查询一条回答详情，校验其属于指定任务 |

路径最终沿用现有 Controller 的统一前缀。接口输入输出使用 `XxxRequest` / `XxxResponse`，显式映射；不直接对外返回持久化实体。异常与分页格式沿用项目现有约定。

## 实施顺序与验收

| 顺序 | 交付内容 | 验收标准 |
|---|---|---|
| 1 | 创建接口、快照及去重 | 2 问题 × 2 渠道 × 2 次得到 8 条结果；重复提交不新增任务；插入失败完整回滚 |
| 2 | 指定渠道调用、响应扩展 | 相同编码/模型的不同渠道 ID 不会选错；原普通查询不受影响；回答及厂商元数据真实回读 |
| 3 | 后台执行与状态汇总 | 全成功、部分失败、全失败准确；失败继续执行；刷新页面不重复调用 |
| 4 | 列表、进度和回答详情 | 能完整走通发起、关闭页面、重新进入、查看回答；分页不丢记录；引用为空正常展示 |
| 5 | 运行时异常与真实联调 | 重启、渠道变更、超时、落库失败不重复调用；小规模真实模型调用与数据库结果对应 |

先使用本地 HTTP 测试替身验证两个协议、参数、引用及失败流程，再进行小规模真实模型联调。单测通过不等于真实模型调用通过。重点验证请求里没有项目背景、没有历史回答，所有重复次数都是独立请求。

方案编辑、渠道停用/配置变更、服务重启、重复提交、数据库异常均需回归。任务创建的批量写入按现有上限核验（最多 200 问题 × 20 渠道 × 10 次 = 40000 条），避免单条循环插入造成过长事务；真实联调先使用少量样本。

## 部署影响与当前验证

- 数据库：沿用已有两张表，创建请求去重字段及唯一索引已落地。已有 011 执行表的库执行 018 一次；新库使用最新版 001 或 011，不重复执行 018。迁移前检查真实表结构，不覆盖已有记录。

- 缓存：计划不新增缓存，无缓存清理步骤。
- 范围：已按第一版实施；定时、取消、失败采样重试与报告留到后续。后台通过数据库会话锁限定唯一执行者，共享库实例需要统一版本。
