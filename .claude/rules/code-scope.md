# 代码生成规范

> 本文件只约束"代码生成的范围与边界"。
> 命名细则见 `rules/naming.md`，结构与重构细则见 `rules/refactor.md`，注释细则见 `rules/comment.md` 及 `rules/comments/`。

# 1. 代码生成目标

代码生成的核心目标：

- 只解决被明确要求的问题
- 生成代码与现有代码风格保持一致
- 不引入任何未被要求的新增能力
- 降低 Review 负担
- 保持代码库简洁可演进

生成代码不是为了展示设计能力。

---

# 2. 核心原则

## 2.1 只做被要求的事

生成代码必须严格对齐需求范围：

- 只实现被明确要求的功能
- 只修改被指定的部分
- 不附带"顺手"的重构
- 不附带"顺手"的格式调整

被要求修复一个 bug，不等于被要求优化周边代码。

---

## 2.2 不引入多余逻辑

禁止在生成代码中出现：

- 未被要求的参数校验
- 未被要求的容错兜底
- 未被要求的日志打印
- 未被要求的监控埋点
- 未被要求的配置开关
- 未被要求的缓存层

这些逻辑会增加理解成本，且往往带来隐含行为。

---

## 2.3 不添加不必要的抽象

抽象、职责拆分、工具类边界的质量标准见 `rules/refactor.md`；命名标准见 `rules/naming.md`。
本节只判断：这些抽象是否应该在本次代码生成中引入。

禁止：

- 为单一调用方创建接口
- 为当前只有一种实现创建抽象类
- 为尚不存在的第二种情况提前做扩展点
- 将本可内联的逻辑拆成单独方法或类

三处以上相似才考虑抽象，否则直接写。

---

## 2.4 不为假想需求设计

禁止：

- 添加"未来可能会用到"的参数
- 预留"后续扩展"的空方法
- 加入"以后可以支持多种策略"的结构

只设计当下确定存在的需求。

---

# 3. 生成前的上下文理解

## 3.1 先读现有代码

生成代码前，必须先了解：

- 同类功能在现有代码中如何实现
- 相关模块使用什么命名风格
- 现有调用方传入的数据结构
- 现有错误处理方式

禁止在未读现有代码的情况下直接生成。

---

## 3.2 遵循已有风格

命名规则以 `rules/naming.md` 为准，方法组织与结构可读性以 `rules/refactor.md` 为准。
本节只约束代码生成时不要混入与现有工程不一致的新风格。

生成代码必须：

- 与已有代码保持一致的命名风格
- 与已有代码保持一致的缩进与格式
- 与已有代码保持一致的错误处理方式
- 使用项目中已有的工具类和基础设施

禁止在同一项目中混入不同风格。

---

## 3.3 避免重复造轮子

生成代码前必须检查：

- 项目中是否已有相同功能的实现
- 依赖库中是否已提供该能力
- 现有工具类中是否已有可复用方法

若已有实现，复用而非新建。

---

# 4. 注释生成规范

注释规则不在本文件重复维护，统一引用：

- 通用注释规则：`rules/comment.md`
- Java 专项注释规则：`rules/comments/comment-java.md`
- Python 专项注释规则：`rules/comments/comment-python.md`

本文件只补充代码生成范围约束：

- 不为展示规范而额外添加注释
- 不为未改动的旧代码补注释
- 不生成与本次需求无关的解释性注释
- 不用注释弥补过度抽象、命名不清或职责混乱

当本文件与注释专题规则发生重叠时，以 `comment.md` 及语言专项规则为准。

---

# 5. 变更范围控制

## 5.1 最小化改动范围

修改已有代码时：

- 只改需要改的行
- 不调整周边无关代码
- 不重新排列方法顺序
- 不统一修改命名风格（命名规则见 `rules/naming.md`，但不能借本次任务顺手批量改名）

变更范围越小，Review 越准确。

---

## 5.2 禁止一次性混合多种改动

一次生成应只做一件事，禁止同时包含：

- 功能修改 + 重构
- 功能修改 + 格式整理
- bug 修复 + 逻辑优化

需要重构时，按 `rules/refactor.md` 另起重构任务或进入对应重构流程，不在普通代码生成里顺手混入。

混合改动会掩盖真实变更意图，增加引入问题的风险。

---

# 6. 禁止生成场景

## 6.1 禁止生成过度防御性代码

例如：

```python
if result is None:
    return None
if result.items is None:
    return []
if len(result.items) == 0:
    return []
```

若系统内部已有保证，不需要每个步骤都做空值防御。

---

## 6.2 禁止生成无用的兼容性代码

禁止：

- 为不存在的旧版本保留兼容入口
- 为没有调用方的接口保留废弃实现
- 为没有触发路径的分支保留默认逻辑

---

## 6.3 禁止生成假设性扩展结构

过度抽象、无语义抽象的判断细则见 `rules/refactor.md`；本节强调没有真实调用方或真实扩展场景时禁止生成。

禁止：

```java
// 目前只有一种策略，未来可能扩展
interface PaymentStrategy {
	void pay();
}

class DefaultPaymentStrategy implements PaymentStrategy {
    ...
}
```

当前只有一种实现时，不需要接口。

---

# 7. Review 检查项

Code Review 时必须检查生成代码是否：

- 引入了需求范围之外的逻辑
- 添加了没有调用路径的抽象
- 添加了不必要的注释
- 修改了超出要求范围的代码
- 混入了重构或格式调整
- 为假想需求预留了扩展点

---

# 8. 最终原则

优秀的生成代码应做到：

- 看 diff 能立刻看出做了什么
- 没有多余的行
- 没有意外的改动
- 与现有代码浑然一体

生成代码应服务于当前问题。

而不是展示设计能力，也不是预测未来需求。
