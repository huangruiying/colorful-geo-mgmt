# Java 注释硬性规则

Java 注释要求以本文件为唯一来源；通用原则见 [comment.md](../comment.md)。本文件的“必须”优先于通用少写废话、范围约束和长度建议。

## 1. 适用范围

- 新增 Java 类必须有类 Javadoc，说明职责、核心入口和边界；首句写法见 1.1。
- 新增或修改的 public/protected 业务方法必须有方法 Javadoc。
- private 方法涉及业务规则、协议适配、状态变化、落库、外部调用、历史兼容或生命周期时，也必须有方法 Javadoc。
- 类、方法和逻辑的检查覆盖本次修改方法的完整内容，不能只看新增行。
- Lombok 生成的纯 getter/setter 无需手写方法注释；字段语义用字段注释说明。简单修改也不免除适用要求。

## 1.1 类注释首句（强制要求）

> 本条为用户确认的强制要求。规则整理、精简、合并或重写时不得删除、弱化或改为建议。

- 类 Javadoc 第一句必须用业务语言直接回答“这个类是什么、管什么”，读者只看这一句就能知道它的用途。
- 第一句不得以“白名单”“迁移边界”“适配”“支撑”等实现视角或抽象词开头。
- 顺序：先写是什么，再写谁在用它、怎么用，最后写约束与边界。约束说明保留，但不能替代第一句。
- 新增类和本次修改涉及的类都适用；类注释首句不满足要求的，按未完成处理。

```java
// 反例：读完整句仍要结合代码才知道用途
/** 项目迁移的固定表和字段白名单；顺序满足外键依赖，不接受文件传入 SQL 标识符。 */

// 正例：首句说清是什么，再写用法和约束
/**
 * 项目导入导出包含哪些表、每张表带哪些字段。
 * <p>每个枚举值对应导出文件中的一个分区和数据库中的一张表：导出按这里的字段读库，校验按这里的字段检查文件，导入按这里的字段写库。</p>
 * <p>约束：表名和字段只取自这里的白名单，不接受文件传入 SQL 标识符；声明顺序父表在前，满足外键依赖。</p>
 */
```

## 2. 方法说明

说明功能、业务目的、实际参数、返回及重要失败语义。
有参数写 @param，有返回写 @return；抛出的检查异常写 @throws，影响调用者处理的业务异常说明原因。不为 void 方法编造返回说明。
对启动/停止等生命周期方法，说明触发时机、资源归属和副作用。

## 3. 识别业务阶段

不能按代码行数、if 数量或是否为入口判断。下列变化通常意味着新阶段：

- 目的：校验 → 查询配置。
- 对象：任务 → 单条回答。
- 来源：入参 → 数据库 → 外部响应。
- 失败语义：输入不合法 → 配置缺失 → 调用失败。
- 动作：查询 → 组装 → 调用 → 判定 → 落库。
- 输出目的：基础对象 → 下游所需上下文。

同一目的连续赋值不是多个阶段；不能为凑编号拆每一行代码。

## 4. 阶段与主流程硬要求

- 只有一个阶段：不强行编号，但仍执行业务决策检查。
- 两个阶段：必须有方法内分段注释。
- 三个及以上阶段：必须按实际顺序使用 // 1.、// 2.、// 3. 编号。
- 方法 Javadoc 不能替代方法内分段或编号注释；抽成小方法也不能省略入口的业务编排说明。

```java
// 1. 校验任务与冻结配置，缺失时拒绝执行
validateTask(task);
// 2. 按指定渠道发送独立问题，不附加历史回答
LLMResponse response = client.query(request, channel);
// 3. 保存本次回答，落库失败不重新调用模型
saveResult(task, response);
```

## 5. 业务决策硬要求

即使只有一个阶段，以下判断也必须按决策组解释业务含义：

- 公共响应和业务响应的判断层次。
- 错误码与状态的优先级、未知状态处理。
- 成功、处理中、失败等核心结果判定。
- 请求与响应标识一致性。
- 重试、限流、历史兼容、降级或兜底为什么存在。
- 并发、锁、启动/停止和资源释放顺序。

同一业务结论的连续条件可以共用一条说明；注释不能只重复条件字面意思。

```java
// 保存失败不能当作模型失败重发，避免同一次诊断重复计费
saveResult(response);
```

## 6. 禁止交付的情况

缺类/方法职责说明、类注释首句未直接说明“是什么”（见 1.1）、缺应有的阶段注释或编号、缺关键决策说明、注释与逻辑不符，均属于未完成。
逐方法检查证据记录方式见 [代码变更流程](../../workflows/code-change-flow.md)；编译、单测和 diff 检查不能替代注释审计。
