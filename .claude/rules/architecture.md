# 架构设计检查

实际目录、分层、命名和已确认模型设计以 [project-conventions.md](project-conventions.md) 为唯一规则源。本文件补充设计判断，不重复定义另一套分层。

## 1. 修改前识别真实职责

- 先确认输入、输出、状态、上下游调用与持久化，不因为类名或 DDD 模板猜职责。
- Controller 接收请求和映射 HTTP 结果；业务编排、核心规则、持久化按项目约定归属。
- 同步接口编排与后台离线 Job 可以分开：触发和生命周期确有区别时保留，不建纯转发层。
- Request/Response 承载接口数据，协议 JSON 解析放在已有通道交互层，不把网络、递归处理或业务编排塞进数据对象。
- 每个新增类/方法必须有实际职责；新增 Service、Controller、流程或转换层前说明必要性与影响，遵守用户已授权范围。

## 2. 简化边界

- 不为每个 CRUD 强制建立独立领域对象，不把 DAO 实体机械复制成同字段模型。
- 不建空占位接口、只有一个调用方的无价值抽象或“将来可能用到”的扩展。
- 字段显式赋值，依赖注入、事务和扫描以项目约定为准。
- 复用现有 HTTP 连接池、线程池、协议模板和持久化能力；生命周期由资源所有者负责，使用方不擅自关闭共享资源。
- 设计调整要检查所有生产者和消费者，不为了局部简化破坏历史接口契约。

## 3. 幂等与事务

- 是否允许“重复跳过”是业务决定，DAO 负责具体插入与冲突处理，数据库唯一约束兜底并发。
- 不在 Controller 写查询/过滤/插入业务编排，不让 DAO 决定与存储无关的业务状态。
- 明确事务范围，外部调用不能因数据库失败被无意重复发送。
- 明确新增、跳过、失败的返回语义，不能把空结果当作幂等成功证据。

## 4. 设计验收

按 [代码变更流程](../workflows/code-change-flow.md) 记录实际分层、抽象必要性、输入输出契约、资源归属、事务/幂等及上下游兼容。
不适用项说明原因；不能只凭编译成功声称架构合理。
