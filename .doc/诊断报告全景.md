# 诊断报告全景

状态：2026-10-17 与用户确认的报告结构；数据表、判定与汇总、接口与页面（① 概览、② 可见度与推荐）已落地，③–⑥ 的汇总与展示待接入。

## 分析口径

- 只分析成功的回答；调用失败、因输出上限截断（`finish_reason=length`）的结果不进入分析。
- 没有来源的回答不参与引用分析，但仍参与提及、推荐与态度分析。
- 各平台“引用”含义不同（豆包/OpenAI 为逐句引用，DeepSeek 为已打开网页，千问/智谱为搜索召回来源，文心为智能搜索网页），引用类指标只在同一口径的平台间比较。
- 以各模型的数据为主，跨模型汇总只作参考。

## 分析场景

同样是分析回答态度，问题类型和回答是否提到目标不同，分析对象与结论不同：

| 问题类型 | 回答提到目标 | 回答没提到目标 |
|---|---|---|
| 点名问题（直接问资产） | A 品牌口碑：模型怎么评价我们 | 几乎不会出现 |
| 非品牌问题（问品类、场景） | B 推荐态度：推荐我们时语气多强、带什么保留 | C 需求与期望：用户在意什么、对这类产品期待什么 |
| 对比问题（我们 vs 竞品） | D 相对评价：哪些方面赢、哪些方面输 | D' 竞品被评价的标准（未被列入对比本身就是问题） |

## 数据结构（2026-10-17 已落地）

报告手动点击生成；判定使用默认渠道（已启用渠道中分数最高者），实际所用渠道记录在报告上。每次生成一份新报告，重新生成不覆盖旧报告，结论可复现、可前后对比。

| 表 | 粒度 | 保存内容 |
|---|---|---|
| `geo_diagnosis_result_output` | 一次报告生成 | 所属诊断任务、生成状态、判定渠道快照、提示词版本、冻结的汇总（指标、主要发现、优化建议）、失败原因 |
| `geo_diagnosis_result_analysis` | 一次报告中的一条有效回答（`output_id` 关联报告） | 判定状态、品牌情感、描述是否准确；`brands`、`points`、`sources` 三个 JSON 数组；失败原因、是否人工修正 |

- 有效回答：诊断结果成功且结束原因不是 `length`（输出截断），创建报告时一次性建立待判定记录。
- 不重复保存可推导的信息：问题分组取诊断快照里的 `brandScope`（方案保存时已做品牌泄露检查）；引用口径由渠道快照中的策略决定；是否有来源、是否实际联网由诊断结果的引用和原始响应判断。这些在生成报告时计算并冻结进汇总。
- 品牌、观点、来源以 JSON 存储：生成报告时在内存中汇总即可；出现跨任务统计需求时再拆表。
- 自有域名暂取项目官网地址，做到 ⑤ 来源分析时再在项目档案中增加自有域名清单。

代码：`GeoDiagnosisResultOutputEntity`、`GeoDiagnosisResultAnalysisEntity`；`GeoDiagnosisResultOutputDao`、`GeoDiagnosisResultAnalysisDao`；领域服务 `GeoDiagnosisResultOutputService.createReport`（锁定任务，校验任务已结束且有成功结果、无正在生成的报告，创建报告并建立待判定记录）；枚举 `DiagnosisReportStatus`、`DiagnosisResultAnalysisStatus`、`DiagnosisBrandSentiment`。建表脚本 `021_geo_diagnosis_report.sql`（旧表名），`022_rename_diagnosis_result_tables.sql` 改为现名并保留数据；新库直接使用 `001_init.sql`。页面、接口与业务概念仍称“诊断报告”，避免与单条“诊断结果”混淆。

## 判定与汇总（2026-10-17 已落地）

后台执行器 `DiagnosisReportWorker` 轮询报告（数据库会话锁 `:diagnosis-report-worker`，开关 `diagnosis.reports.enabled`，默认开启），优先续跑中断的 RUNNING 报告，其次领取最早的 PENDING 报告：

```text
冻结判定渠道（首次：默认渠道 = 已启用渠道中分数最高者；续跑：沿用快照中的同一渠道）
逐条待判定记录：
  ① 规则（DiagnosisResultRuleAnalyzer）：来源归类 我方发布 → 自有域名 → 标题提到目标 → 标题提到竞品 → 其他，附平台名称
  ② 判定（DiagnosisResultAnalysisPrompt，提示词 v1）：一次调用拿全部字段，按问题分组只填适用部分
  ③ 校验：品牌名统一（目标统一为项目名，竞品简称归到预设名，对不上的为待确认产品）；观点原文片段去掉空白和 Markdown 符号后必须出现在回答中，否则丢弃
  ④ 保存成功或失败；失败不重试，来源归类照样保存
全部判定结束：维度归一（1 次调用，失败保持原名）→ 汇总（DiagnosisReportSummarizer）→ summary 冻结 → SUCCEEDED
判定全部失败 → FAILED；汇总异常 → FAILED（不反复重试，避免重复计费）
```

**summary 结构**：`sample`（有效回答、判定成功和失败数、带来源数、实际联网数、模型数、题数、最大采样次数、判定渠道、提示词版本）、`models`（每个模型一行：非品牌问题的提及率、推荐率、首推率、平均排名、问题覆盖率、稳定性；点名问题的品牌正面率；非品牌与对比问题的推荐份额）、`strength`（提到目标时的推荐强度分布）、`reservations`（目标的保留意见）、`criteria` 与 `concerns`（非品牌且未提到目标的回答中的选择标准与顾虑）、`byIntent`。排行按归一维度计数，每项最多 3 条原文示例。比率保留 4 位小数，分母为 0 时为 null。

**判定渠道要求**：用不推理的快速模型。2026-10-17 实测：`qwen3.6-plus`（默认深度思考）每条 56–115 秒，超过服务统一 60 秒 HTTP 超时；`qwen-plus` 每条 10–34 秒。判定输出约 500–1000 token，渠道输出上限过小（如 1400）会被截断判失败。

**实测（6 条真实回答，两个被测模型、三类问题，判定模型 qwen-plus）**：全部解析成功；观点保留 31/36，丢弃的为跨段拼接引用；竞品名称全部归到预设名；汇总数字人工核对一致。

## 接口与页面（2026-10-17 已落地）

| 接口 | 说明 |
|---|---|
| `POST /diagnosis-reports` `{taskId}` | 为一次已结束且有成功回答的诊断任务生成报告，返回 201 与判定进度；任务未结束、已有报告在生成、没有有效回答时 400 并说明原因 |
| `GET /diagnosis-reports?taskId=&status=&page=&size=` | 报告列表，最新在前，含方案与项目名称（取自任务快照）、状态、判定进度；不含汇总 |
| `GET /diagnosis-reports/{id}` | 报告详情，完成后含冻结的 `summary` |

页面 `history-report.html`（导航「诊断报告」）：
- 「生成诊断报告」按钮：选择一次诊断任务（只列已结束且有成功回答的任务）后生成。
- 诊断任务详情中，已结束且有成功回答的任务显示「生成报告」，跳转到报告页并预选该任务。
- 报告列表与详情在生成中每 3 秒刷新判定进度。
- 详情按 6 个子 Tab 展示：① 诊断概览（样本说明、各模型核心指标）、② 可见度与推荐（可见度指标、推荐强度、保留意见、选择标准、用户顾虑、按意图拆分）已接入，原文示例可点开查看回答；③–⑥ 显示“待接入”。
