# 日志规范

# 1. 日志目标

日志的核心目标：

- 还原关键流程
- 快速定位问题
- 追踪状态变化
- 支撑排障与审计
- 降低线上问题定位成本

日志不是为了打印而打印。

---

# 2. 核心原则

## 2.1 只记录有价值的信息

日志应优先记录：

- 关键业务动作
- 状态切换
- 外部依赖调用
- 失败原因
- 重试过程
- 降级行为

禁止大量打印无意义过程日志。

---

## 2.2 一条日志应尽量说明上下文

日志应尽量包含：

- 业务标识
- 请求标识
- 关键参数
- 执行结果
- 耗时

例如：

```text
orderId=12345 traceId=abc123 status=PAID costMs=82
```

---

## 2.3 日志应稳定可检索

推荐：

- 固定关键词
- 固定字段名
- 固定结构
- 固定错误描述模式

避免：

- 同一类问题多种写法
- 纯口语化描述
- 只写一句看不出上下文的话

---

# 3. 日志级别规范

## 3.1 ERROR

用于：

- 当前操作失败
- 影响主流程执行
- 需要人工关注
- 出现未预期异常

例如：

- 下单失败
- 数据库写入失败
- 第三方调用最终失败

---

## 3.2 WARN

用于：

- 出现异常但系统可继续运行
- 发生重试
- 命中降级
- 数据异常但已兜底
- 发现潜在风险

例如：

- 接口第一次调用超时，进入重试
- 配置缺失，回退默认值

---

## 3.3 INFO

用于：

- 关键业务动作开始或完成
- 核心状态切换
- 重要外部调用结果
- 需要长期保留的流程节点

禁止把所有细节都打成 INFO。

---

## 3.4 DEBUG

用于：

- 本地调试信息
- 临时问题排查信息
- 高频细节数据

DEBUG 日志默认不应依赖线上长期保留。

---

# 4. 必须打日志的场景

以下场景必须记录日志：

- 状态切换
- 外部接口调用失败
- 重试触发与结束
- 降级触发
- 异常捕获边界
- 定时任务开始与结束
- 消费消息失败
- 风控拦截
- 关键业务动作完成

---

# 5. 外部调用日志规范

调用第三方、数据库、缓存、消息队列等外部依赖时，建议记录：

- 调用目标
- 调用结果
- 耗时
- 重试次数
- 失败原因

推荐：

```java
log.warn("invoke payment failed, orderId={}, retryCount={}, costMs={}", orderId, retryCount, costMs, ex);
```

禁止：

```java
log.info("调用失败");
```

---

# 6. 异常日志规范

## 6.1 异常应在边界统一记录

原则：

- 能继续向上抛出的异常，不要层层重复打印
- 在真正处理异常的位置记录日志
- 避免一条异常打印多次造成噪音

---

## 6.2 日志内容必须可定位

异常日志至少应说明：

- 哪个业务动作失败
- 哪个关键对象失败
- 当前处于什么阶段
- 异常原因是什么

不推荐：

```java
log.error("error", ex);
```

推荐：

```java
log.error("create order failed, userId={}, skuId={}", userId, skuId, ex);
```

---

# 7. 禁止打印的内容

严禁打印：

- 密码
- token
- cookie
- 密钥
- 身份证号
- 手机号全量
- 银行卡号
- 隐私信息
- 超大对象完整内容
- 整包请求体与响应体

必要时必须脱敏。

---

# 8. 禁止日志场景

## 8.1 禁止把日志当注释

错误示例：

```java
log.info("进入方法");
log.info("开始循环");
log.info("循环结束");
```

这种日志不能提供真实排障价值。

---

## 8.2 禁止高频无意义日志

例如：

- 循环内逐条打印普通数据
- 心跳日志无节制输出
- 每次缓存命中都打印 INFO

高频路径必须控制日志量。

---

## 8.3 禁止只打成功不打失败

日志必须能帮助判断：

- 成功了什么
- 失败了什么
- 为什么失败
- 是否进行了重试或降级

---

# 9. Review 检查项

Code Review 时必须检查：

- 是否遗漏关键流程日志
- 日志级别是否合理
- 日志内容是否可检索
- 是否存在重复打印同一异常
- 是否打印敏感信息
- 是否存在高频噪音日志

---

# 10. 最终原则

优秀日志应做到：

- 出问题时能快速定位
- 看日志就能还原关键流程
- 关键信息完整
- 噪音尽量少

日志应服务排障与审计。

而不是制造新的阅读负担。
