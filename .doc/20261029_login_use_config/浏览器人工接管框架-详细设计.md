# 【浏览器自动化】浏览器人工接管框架与预发布后台执行 - 详细设计

> 需求编号：待定。一期（预发布后台执行）2026-10-30 完成；二期（浏览器人工接管框架 + 人工验证场景，搜狐号试点）2026-10-31 完成；三期（其他平台接入人工验证）未开始。

# 需求背景

浏览器自动化（预发布、登录）在执行中会遇到平台的人机验证：滑块拼图、短信安全验证、图形验证码等。典型案例是搜狐号：新设备打开编辑器会跳到 `/mpfe/v4/clientAuth`，点“获取验证码”后弹出腾讯滑块（`turing.captcha.gtimg.com`）。部署到服务器后，出口 IP 和机器环境变化，这类验证大概率会再次出现，而服务器上没人看得见浏览器。

现状有两个问题：

1. 遇到验证只能失败，用户无法在服务器上完成验证。
2. 批量预发布在一次 HTTP 请求里同步执行全部平台。中途若要等人工验证（可能几分钟），请求会被 Nginx 等代理按超时断开，页面关闭也会中断。

**术语（2026-10-31 用户确认）：**

- **浏览器人工接管**（框架，技术）：服务器上的 Playwright 页面需要人时，把实时画面推到管理页，用户在画面上点击、拖动、输入，操作转发回服务器页面，直到调用方给出的完成条件满足。框架不认识平台和业务。
- **场景**（业务侧）：决定什么时候请求接管、怎样算完成、完成后做什么。目前只有“人工验证”一个场景：页面停在平台验证上时请求接管，验证消失即算完成。

**核心语义：**

- 不识别验证码、不模拟拖动轨迹、不伪造或转交验证票据。验证一律由用户本人在平台的真实页面上完成。
- 自动化识别到验证 → 请求人工接管，当前平台暂停 → 任意管理页弹出接管窗口 → 用户在窗口里操作真实页面 → 验证消失后自动继续。
- 超时或用户放弃 → 该平台记为失败并写明原因；同批次其他平台不会因此失败（后台任务单线程，接管期间它们排在后面执行）。

**什么时候需要接管：**

| 情况 | 例子 | 处理 |
|---|---|---|
| 代码能自动处理 | 推广弹窗、协议勾选 | 写在平台适配代码里，不接管 |
| 要人做，但能通过管理页表单转交 | 选验证方式、填短信码（抖音扫码登录后的身份验证） | 管理页表单转交，不接管 |
| 要人做，且必须直接在平台页面上操作 | 拖滑块、点选图片 | 浏览器人工接管 |

出现频率不影响判断：一次性的验证只要发生在服务器上、且必须直接操作页面，也只能靠接管完成。没有真实需求的场景不提前做。

**本方案目标：**

- 浏览器人工接管与业务隔离：框架只认页面、标题、原因、完成条件和超时；以后有新场景，新增场景代码调用框架即可，框架不改。
- 预发布改为后台执行，提交后立即返回，页面轮询结果；部署后不再受请求超时影响。
- 分三期交付：一期后台执行；二期接管框架 + 人工验证场景，以搜狐号试点；三期其他平台接入人工验证。

# 实现逻辑

## 整体逻辑

```Plain Text
提交预发布 ──> 插入发布记录（初始化）──> 立即返回
                         │
          预发布后台任务领取“初始化”记录，逐平台执行
                         │
    ┌────────────────────┼─────────────────────┐
  知乎：正常完成     搜狐号：识别到验证        哔哩哔哩：正常完成
                         │
      人工验证场景请求浏览器人工接管，当前平台线程驱动接管
                         │
   任意管理页的全局脚本轮询到待接管 → 弹出接管窗口
   画面：CDP Page.startScreencast 推帧；操作：Input.dispatch* 转发
                         │
     用户点按钮 / 拖滑块 / 填短信 ──> 验证消失 ──> 继续存草稿
                         │
          超时 / 放弃 ──> 该平台记为失败（写明原因）
```

### 一期：预发布后台执行

- 提交接口只做校验、插入发布记录（状态“初始化”），立即返回当前记录列表。
- 预发布由同步改为异步：新增后台 Job `presentation/task/ContentPrePublishWorker`，与 `DiagnosisTaskWorker` 同包、同做法，使用 `ThreadPoolConfig` 中新增的专用线程池。
- Job 定时扫描状态为“初始化”（待发布）的发布记录；领取用带状态条件的更新（`WHERE status = 初始化` 改为“预发布中”），更新成功才算领到，保证同一条记录只执行一次。领到后调用平台策略，结果写回记录。执行顺序仍为逐平台串行。
- 服务重启时，遗留的“预发布中”记录保持原状态：该状态本身即表示“结果待核对”（与原同步执行时请求中断的结果一致），不自动重试，避免重复建稿。因此不需要诊断任务那样的数据库会话锁；防重复执行由领取时的条件更新保证，多实例同时领取也只有一个成功。
- 实现（2026-10-30 已完成）：`ContentPrePublishWorker`、`ThreadPoolConfig.prePublishTaskExecutor`（单线程）、`ContentPublishRecordService.claimNextInitializedRecord`（替代原 `startPrePublish`）、`ContentPublishBusiness.prePublish` 只建记录；页面轮询最长 15 分钟，超过视为待人工核对。
- 内容优化页、发布记录页对“初始化 / 预发布中”的记录定时轮询（3 秒），直到终态。

### 二期：浏览器人工接管框架 + 人工验证场景（2026-10-31 已完成）

| 层 | 位置 | 职责 |
|---|---|---|
| 框架 | `infrastructure/client/playwright/takeover/` | `BrowserTakeoverRegistry`：登记表与唯一入口 `requestTakeover(页面, 标题, 原因, 完成条件)`，返回已完成 / 已放弃 / 超时；`BrowserTakeover`：一次接管的登记信息与跨线程数据；`BrowserTakeoverSession`：CDP 画面与操作通道；`BrowserTakeoverInput` / `BrowserTakeoverFrame`：操作与画面；`BrowserTakeoverOutcome`：结局。不引用平台、业务枚举 |
| 场景：人工验证 | `takeover/verification/` | `HumanVerificationRule`：识别规则；`HumanVerificationTakeover.ensureHumanVerified(页面, 平台, 业务名称)`：识别到验证就以“平台 · 业务”为标题、规则原因为说明请求接管，验证消失为完成条件；没有验证返回“无需人工接管”，不发起接管 |
| 业务接入 | 平台客户端 | `SohuBrowserClient`：打开编辑器遇到 `/clientAuth` 时调用人工验证场景；完成后写回登录态并重新打开编辑器；放弃或超时抛 `PublicationClientException` |
| 接口 | `presentation/controller/MgmtBrowserTakeoverController` | `/browser-takeovers`：列表、画面、操作、放弃 |
| 前端 | `static/admin/shared/browser-takeover.js` | 12 个管理页引入，样式在 `styles/components.css` |

实现要点：

- **线程模型**：Playwright 对象只能在创建它的线程使用，HTTP 线程不能操作页面。请求接管的后台线程每 100ms 循环一次：转发窗口放入的操作、确认截图帧、检查完成条件；HTTP 线程只读最新帧、放入操作、标记放弃。登记表中的记录不含 Page。完成条件检查时页面正在跳转、读取失败，按未完成处理，下一轮再判断。
- **识别规则只收录实际核对过的**：`SOHU_CLIENT_AUTH`（URL 含 `/mpfe/v4/clientAuth`，仅搜狐号）、`TENCENT_CAPTCHA`（`iframe[src*='turing.captcha']` 可见，通用）。平台专属规则在前，同时命中时用它的原因。其他验证实际遇到、核对页面特征后再加。
- **结束即移除**：完成、放弃、超时后记录立即移除，窗口取画面得到 404 即关闭；第一帧未到时返回 204。
- **操作**：只支持鼠标左键，按住左键时的移动由服务端带上左键（拖动）；功能键白名单为 Backspace、Tab、Enter、Escape、Delete 和方向键；文字一次最多 100 字；未转发的操作最多积压 200 条。
- **截图**：窗口在看（5 秒内取过画面）时才截图，JPEG 质量 60、最大 1280×900；窗口关闭后停止截图，记录继续等待。
- **搜狐号试点**：验证完成后把带验证结果的浏览器会话写回 `platform_browser_login.storage_state`（`PlatformBrowserLoginDao.updateStorageState`，只更新已登录记录），下次预发布不再要求验证；重新打开编辑器仍被要求验证则失败，不循环等待。放弃或超时报“搜狐号安全验证未完成：已放弃人工接管 / 等待人工接管超时”。
- **前端**：每 3 秒查待接管列表，一次只弹一条；窗口每 80ms 取帧（服务端每 100ms 确认一次截图，新画面最多约每秒 10 帧）；操作串行发送，连续移动只保留最新一次；“稍后处理”只在本页不再弹出该条，换页或刷新后再次弹出；ESC 不关窗口（留给远程页面）。

### 二期交互流程

**原则：平时不推画面，需要接管时才推；页面始终主动去拉，服务器不主动推送。**

#### 1. 接管登记表

`BrowserTakeoverRegistry` 是 Spring 单例，整个进程只有一份，内部为线程安全 Map：

```Plain Text
接管 ID（随机 UUID） → 接管记录 BrowserTakeover
                        ├─ 标题（如“搜狐号 · 预发布”）、原因、开始时间、截止时间
                        ├─ 最新一帧画面（开始截图后才有，只保留最新一帧）
                        ├─ 待转发的操作队列
                        └─ 是否已放弃
```

后台任务线程与 HTTP 请求线程在同一个 Java 进程里，注入的是同一个单例，因此无需数据库、Redis 或其他缓存来传递“需要展示”的消息。

#### 2. 完整流程

| 步骤 | 执行方 | 动作 |
|---|---|---|
| 1. 识别 | 后台任务线程（如预发布 Job） | 平台客户端调用 `ensureHumanVerified(页面, 平台, 业务名称)`，按 `HumanVerificationRule` 判断页面处于验证；未识别到则直接继续，不登记、不截图 |
| 2. 请求接管 | 后台任务线程 | 场景调用 `requestTakeover(页面, 标题, 原因, 完成条件)`，生成 UUID 写入 Map，开始循环，最长 10 分钟。此时仍不截图 |
| 3. 发现 | 任意管理页的公共脚本 `shared/browser-takeover.js` | 每 3 秒 `GET /browser-takeovers`；Controller 注入同一个登记表，直接读 Map 返回。有记录即弹出窗口（一次一条，按登记顺序） |
| 4. 开始推画面 | 弹窗 → 服务器 | 窗口取画面后，后台线程下一轮对该页面开启 CDP `Page.startScreencast`；页面每变化一次产生一帧，记录中只保留最新一帧 |
| 5. 显示画面 | 弹窗 | 约每 80ms 拉取一次最新帧，按 `sequence` 跳过旧帧，绘制到窗口的 `<canvas>` 上 |
| 6. 用户操作 | 弹窗 → 服务器 | 每个点击、拖动、滚轮、输入单独 `POST /browser-takeovers/{takeoverId}/input`，放入操作队列；后台线程下一轮用 CDP `Input.dispatchMouseEvent` / `Input.insertText` 等作用在真实页面 |
| 7. 判断完成 | 后台线程 | 每轮检查完成条件（人工验证：验证消失）；满足则停止截图、从 Map 删除 |
| 8. 结束 | 弹窗 / 后台线程 | 弹窗下次取帧得到 404 后关闭；后台线程返回“已完成”，平台客户端继续执行（如存草稿） |

#### 3. 其他结局

- **放弃**：弹窗点“放弃接管” → `POST /browser-takeovers/{takeoverId}/abandon` → 后台线程下一轮结束等待、停止截图、删除记录，该平台记为失败（原因“已放弃人工接管”）。放弃前积压的操作不再执行。
- **超时**：10 分钟未完成 → 处理同“放弃”，原因“等待人工接管超时”。
- **窗口关闭但未放弃**：停止取帧后服务器停止截图；记录继续排队，再次打开任意管理页会重新弹出，直到完成、放弃或超时。
- **无人打开管理页**：记录在 Map 中排队等待，超时后失败；同批次其他平台排在其后，超时后照常执行。

#### 4. 为什么只放内存

正在接管的浏览器页面只能存在于当前 Java 进程，无法序列化到数据库或 Redis。代价：

- 服务重启：Map 清空，对应浏览器也随进程关闭，相关平台按“结果待核对”处理。
- 多实例部署：请求可能落到没有该浏览器的实例，需另做请求路由；当前为单实例部署，不受影响。

### 三期：推广

- 其余预发布客户端在打开编辑器、保存后等关键步骤调用 `ensureHumanVerified`，遇到验证时由“直接失败”变为“人工接管”。
- 登录流程：扫码、表单、抖音身份验证目前已由代码或登录页表单处理，暂不需要接管；登录中途在服务器上遇到滑块时再接入人工验证场景。
- 识别规则：实际遇到并核对页面特征后加到 `HumanVerificationRule`；什么值得买、一点资讯见过腾讯验证码，通用规则可覆盖。
- 新场景：按“什么时候需要接管”的判断标准确有需求时，新增场景代码调用 `requestTakeover`，框架不改。

# 接口文档

## 接口基础信息

### 提供接口的服务

colorful-geo-mgmt 管理后台（需登录，写请求带 `X-XSRF-TOKEN`，前端统一走 `AdminHttp.requestJson`）。出错统一返回 Spring `ProblemDetail`，原因在 `detail` 字段。

### 服务域名

与管理后台同域。

## 接口一：提交预发布（语义变更）

接口地址：POST /content-publish/{id}/pre-publish（现有路径，不改）

**Request**

无新增字段。

**Response**

无新增字段。返回时各平台记录为“初始化”或“预发布中”，不再等待平台结果；页面需轮询发布记录直到终态。

## 接口二：待人工接管列表

接口地址：GET /browser-takeovers

**Request**

无。

**Response**

```JSON
[
  {
    "takeoverId": "c6f2…",
    "title": "搜狐号 · 预发布",
    "reason": "搜狐号要求对本浏览器做短信安全验证",
    "startedAt": "2026-10-31T02:00:00Z",
    "expiresAt": "2026-10-31T02:10:00Z"
  }
]
```

| 字段 | 类型 | 说明 |
|---|---|---|
| takeoverId | string | 接管标识（随机串，非数据库 ID），后续接口用它定位 |
| title | string | 接管对象，由场景给出；人工验证场景为“平台 · 业务” |
| reason | string | 需要人工的原因，由场景给出 |
| startedAt | string | 登记时间（UTC） |
| expiresAt | string | 等待期限（UTC），到期后原业务按超时失败 |

没有待接管时返回空数组。

## 接口三：接管画面

接口地址：GET /browser-takeovers/{takeoverId}/frame

**Request**

无。

**Response**

```JSON
{
  "imageBase64": "…",
  "width": 1280,
  "height": 720,
  "sequence": 128
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| imageBase64 | string | 服务器页面截图（JPEG）的 Base64 |
| width | number | 页面宽度（CSS 像素），前端据此把点击位置换算成页面坐标 |
| height | number | 页面高度（CSS 像素） |
| sequence | number | 帧序号，递增；前端据此跳过已画过的帧 |

第一帧还没到时返回 204；首次调用后服务器才开始截图，5 秒内没人取画面即停止截图。传输方式为短轮询（约 80ms）；每次都返回当前最新一帧，未变化时前端按 `sequence` 跳过。

## 接口四：转发操作

接口地址：POST /browser-takeovers/{takeoverId}/input

**Request**

```JSON
{
  "type": "MOUSE_MOVED",
  "x": 512,
  "y": 380,
  "deltaX": 0,
  "deltaY": 0,
  "text": null,
  "key": null
}
```

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| type | string | 是 | 无 | `MOUSE_PRESSED` / `MOUSE_MOVED` / `MOUSE_RELEASED` / `MOUSE_WHEEL` / `INSERT_TEXT` / `KEY_PRESS`；只支持左键，按住左键时的移动即拖动 |
| x, y | number | 鼠标与滚轮必填 | 0 | 页面坐标（CSS 像素），0～10000 |
| deltaX, deltaY | number | 否 | 0 | 滚动量，仅 `MOUSE_WHEEL` 使用 |
| text | string | `INSERT_TEXT` 必填 | 无 | 在当前焦点处输入的文字，1～100 字 |
| key | string | `KEY_PRESS` 必填 | 无 | Backspace、Tab、Enter、Escape、Delete、ArrowLeft、ArrowUp、ArrowRight、ArrowDown |

**Response**

204，无正文。按提交顺序作用到该接管对应的页面。

## 接口五：放弃接管

接口地址：POST /browser-takeovers/{takeoverId}/abandon

**Request**

无。

**Response**

204。原业务随即结束等待并按失败处理，原因“已放弃人工接管”。

## 错误码

| HTTP 状态码 | 说明 | 处理建议 |
|---|---|---|
| 400 | 操作不合法（类型缺失、坐标越界、文字为空或超长、按键不在白名单）或积压操作超过 200 条 | 展示 `detail`，不重发 |
| 404 | 接管已完成、放弃、超时或不存在（`detail`：人工接管已结束或不存在） | 关闭接管窗口 |
| 401 | 未登录 | 由 `AdminHttp` 跳转登录页 |

# 发版影响分析

### 阶段一：一期代码上线，后台任务开启

代码：预发布提交即返回，后台任务逐平台执行；平台调用逻辑不变。
DB：无变更。Redis：不涉及。
影响：提交后页面先显示“预发布中”，结果需等轮询刷新；服务重启时正在执行的平台按“结果待核对”处理，与现状一致。

### 阶段二：二期代码上线，仅搜狐号接入人工验证

代码：搜狐号遇到 `/clientAuth` 时请求人工接管；其他平台行为不变。
DB：无 DDL；搜狐号验证完成后更新 `platform_browser_login.storage_state`。Redis：不涉及。
影响：无人处理时，搜狐号等待最长 10 分钟后失败；预发布后台任务为单线程，等待期间同批次其他平台排在其后，超时后继续执行。

### 阶段三：其他平台逐步接入人工验证

代码：按平台逐个在关键步骤调用 `ensureHumanVerified`。
DB：无变更。Redis：不涉及。
影响：接入的平台遇到验证时由“直接失败”变为“人工接管”；未接入的平台不变。

# 灰度顺序

1. 上线一期，在测试账号上提交多平台预发布。验证：提交立即返回，页面状态从“预发布中”变为终态，发布记录与平台草稿一致。
2. 观察一期运行，确认无重复建稿、无记录卡在“初始化”。验证：日志中每条记录只被领取一次。
3. 上线二期，搜狐号使用新部署服务器的登录态预发布。验证：日志出现 `browser takeover requested`，管理页弹出接管窗口，画面清晰，可在窗口中完成滑块和短信；日志出现 `outcome=COMPLETED` 后草稿创建成功。
4. 实测放弃和超时。验证：搜狐号记录为失败并写明原因，其他平台正常完成。
5. 逐个平台接入三期识别规则。验证：各平台遇到验证时弹窗出现，未遇到时无额外等待。

# 测试关注点

- 提交多平台预发布，是否立即返回，且每条记录最终进入终态
- 服务在“预发布中”时重启，是否保持待核对且不自动重新建稿
- 后台任务开关关闭时，提交的记录是否停在“初始化”且不调用平台
- 页面未遇到验证时，`ensureHumanVerified` 是否直接返回、不登记接管
- 搜狐号跳转 `/clientAuth` 时，是否请求接管并在任意管理页弹窗，标题为“搜狐号 · 预发布”
- 接管窗口中点击、拖动、输入，是否作用在服务器页面的对应位置（含窗口缩放换算）
- 验证完成后是否自动关闭窗口、写回登录态并继续存草稿
- 超时、放弃后，该平台是否记为失败且原因可读，同批次其他平台是否照常完成
- 多条待接管是否按顺序逐条弹出；“稍后处理”后换页是否再次弹出
- 画面帧、操作事件是否不写入日志，接口是否要求管理员登录与跨站令牌
