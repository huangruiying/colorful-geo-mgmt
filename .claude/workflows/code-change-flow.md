# 代码变更执行与验收流程

适用于新功能、修复、重构及代码生成；也是 A/D/E 的共同实现与验收阶段。流程不复制语言和架构硬规则，只规定加载时机、执行顺序和完成证据。

## 1. 接手与范围确认

- 核对 AGENTS.md、HANDOFF、Git 状态、相关差异；保留用户已有改动。
- 明确目标、已有能力、缺口、范围和验证方法。超过简单修改先确认，已有授权持续有效。
- 新需求由 A 补需求与接口边界；纯实现不重复设计，不新增无必要的中间层。

## 2. 编码前懒加载

必读：项目约定、comment.md、refactor.md、code-scope.md。
按修改动作加载下表，当前会话已完整读过且未变化的文件复用；引用不代表读取。

| 触发条件 | 追加读取 |
|---|---|
| 新增/修改 Java | comments/comment-java.md |
| 新增/修改 Python | comments/comment-python.md |
| 新增类、跨层调整、线程/事务/资源变化 | architecture.md |
| 新增/修改接口、类、方法或字段命名 | naming.md |
| 日志、外部调用或异常处理 | logging.md、error-handling.md |
| 测试实现 | testing.md |
| 接口文档 / 技术设计文档 | api-doc.md / tech-design-doc.md |
| 支付通道适配 | channel-integration.md、channel-modeling.md |
| 其他外部请求/响应建模 | channel-modeling.md |

进入当前阶段时读取 04-code-generation 或 05-refactor；不提前加载全部 Agent。
开始修改前简要声明适用规则和范围。

## 3. 实现与自检

- 复用已有能力，按实际边界编排，不增无必要抽象。
- 边实现边识别业务阶段，按语言规则写职责、阶段、决策和生命周期注释。
- 修改方法后检查完整方法及相关调用链，同步失真的名称、注释、接口、SQL和资源引用。

## 4. 逐方法注释审计（必须完成）

对每个新增/修改业务方法记录：

| 方法 | 阶段数量与目的 | 方法说明 | 分段/编号 | 决策/兼容/生命周期说明 | 结果 |
|---|---|---|---|---|---|
| 文件路径#方法名 | 逐项写实际目的 | 通过/缺失 | 通过/不适用及原因 | 通过/不适用及原因 | 通过/待修正 |

类职责和边界另检查一次，包括类注释首句是否直接说明“是什么”（[comment-java.md](../rules/comments/comment-java.md) 1.1）。检查范围是完整变更方法，不只新增行。
审计是读取代码后得出的证据，不能只写“按规范检查通过”，不能靠注释行数或编译结果替代。
小任务可在交付回复中记录；较多方法记录到当前交接或验收文档，不写长期 memory。
出现缺漏先修正再交付，不把“后续补注释”作为完成。

## 5. 架构复核（适用时必须完成）

记录修改涉及的真实层与职责、抽象必要性、数据对象边界、资源所有者、事务/幂等、上下游契约。
纯注释/样式修改可标为不适用并说明原因；依照 architecture.md 与项目约定检查，不照通用 DDD 模板增加层次。

## 6. 验证与独立复核

- 进入 06-unit-test-gen 视角，验证实际行为与边界；检查测试是否必要、有意义，不写镜像实现的机械测试。
- 运行与本次变化相称的检查。编译/单测/真实联调分别记录；无法运行说明具体阻断。
- 再进入 09-code-review 视角，复核差异、注释审计和架构证据，缺漏回实现阶段修正。
- 明确要求全量或真实接口回归时才进入 F；不将单测包装成平台联调。
- 有真正独立任务并获授权才启动子代理，角色切换本身不要求多代理并行。

## 7. 交付

结果、变更文件、注释/架构检查证据、验证和限制必须可复核。
重要工作更新 HANDOFF；不强制五个英文栏目，不重复贴全部规则。
