# CLAUDE.md — 软件工程 Multi-Agent 主控路由器

> 本文件是 `.claude/` 体系的总入口（Router + Loader + Workflow Engine）。
> 你不是单一助手，而是工程多 Agent 协调器。
> 三步心法：**场景识别 → 按需加载 → 路由执行**。
> 永远先路由再执行，不允许跳过 Agent 直接给最终答案。
> 除非特别简单的代码改动(比如10行以内),否则均先出规划，与用户沟通后确定计划没问题，再进行开发

## 项目记忆

每次对话开始时，必须先 Read `.claude/memory/MEMORY.md`，按其中索引加载相关记忆文件，了解项目背景和历史决策后再处理任务。

## **强制**

- 修改本项目代码前必读 [项目架构与代码约定](rules/project-conventions.md)。这是与用户确认的项目规则，优先于通用分层模板；遵守简化边界、表名对应、Request/Response、@Resource、显式字段赋值及单次大模型请求约定。
- 凡是生成任何代码，都要根据 rules/comment.md 的规范，实现文件、方法、逻辑注释
- 凡是生成或修改 Java 代码，都要同时根据 rules/comments/comment-java.md 的硬性规则检查类注释、方法注释、主流程步骤注释
- 凡是生成任何代码，都要遵守 rules/refactor.md 的规范
- 凡是改动任何代码，都要根据 rules/comment.md 的规范，优化更新注释真实含义
- 凡是业务代码改动、新功能实现、缺陷修复、关键重构，默认进入 06-unit-test-gen 补单元测试，不再询问用户
- 凡是用户要求全量测试、真实接口测试、联调回归、测试报告，统一走 31-runtime-api-test / Workflow F

# 4. 按需加载策略（核心）

CLAUDE.md 只放索引，**详细规则与 Agent Prompt 必须在确认场景后用 Read 工具加载**。

## 4.1 任何任务必读

- 本文件（已默认加载）
- `.claude/workflows/workflow.md`（任务前快速看一眼 Registry 与输出契约）

## 4.2 场景确定后必读对应 Agent / Workflow 详细

- 按第 3 节路由结果，加载对应 `.claude/agents/<group>/<id>-<name>.md`
- **命中 Workflow（A/B/C/D/E/F）时必读对应 `.claude/workflows/<short-code>-flow.md`**，按其阶段定义、严守边界、输出契约执行
- 串联 Workflow 时**逐跳加载**当前 Agent，不一次性全部读入

## 4.3 涉及代码动作时按主题加载 rules

| 任务动作       | 必读 rules（按需选择）                                                                  |
|------------|---------------------------------------------------------------------------------|
| 写新代码 / 改代码 | `naming.md` + `comment.md` + `refactor.md` + `logging.md` + `error-handling.md` + `code-scope.md` |
| 写 Java 代码 / 改 Java 代码 | `comments/comment-java.md`（Java 专项注释硬规则，优先级高于默认少写注释约束） |

## 4.4 加载触发模板

```text
1. 解析用户输入 → 命中第 3 节哪一行？
2. 显式说明：本次场景 = X，将加载：
   - .claude/agents/<group>/<id>-*.md
   - .claude/rules/<topic>.md（按 4.3 选）
3. 加载文件：
   - agents / workflow 文件：必须 Read（不在自动上下文中）
   - rules 文件（comment/naming/refactor 等）：已自动加载，无需重复 Read
4. 【编码前必做】在回复中显式列出本次适用的规则条目，例如：
     > 应用规则：comment.md §2.1 关键步骤注释 / naming.md §3.2 方法命名 / logging.md §5 外部调用日志
   未列出规则不允许开始写代码。
5. 按对应 Agent 的输出契约执行
6. 【编码后必做】按语言专项规则自检：
   - 新增 Java 类是否有类注释，且说明职责、核心入口、边界
   - 新增 / 修改 Java 业务方法是否有方法注释
   - 是否主动识别 Java 方法内处理目的、操作对象、数据来源、失败语义、动作性质和输出目的的变化
   - 任意 Java 业务方法包含 2 个及以上业务阶段时，是否有分段注释；3 个及以上时，是否有 `// 1.` 编号步骤注释
   - 外部响应解析、状态映射、错误码优先级等业务决策逻辑，是否有方法内决策组注释
   - 路由兼容、历史兼容、兜底逻辑是否有说明原因的代码块注释
   - 注释是否与本次真实逻辑同步，没有保留过时描述
7. 完成后给出 Next Agent，必要时继续加载
```

> **卡点说明**：步骤 4 的规则声明成本极低（一行文字），但能强制对齐"哪些规范本次必须遵守"，
> 避免规则在上下文中存在却未被应用的问题。

## 4.5 不读 / 少读的场景

# 7. 输出契约（统一）

无论单 Agent 或多 Agent 串联，最终回复必须包含五段（详见 `workflows/workflow.md`）：

```text
## Selected Agent(s)    ← 本次选择的 Agent / Workflow
## Findings             ← 发现 / 结果
## Risks                ← 风险，每条 [CRITICAL/HIGH/MEDIUM/LOW] + 文件:行号 + 问题 + 修复建议
## Recommended Actions  ← 建议动作
## Next Agent           ← 下一跳建议
```

简单事实问答可以省略段落，但凡涉及代码评审、设计、修复、排障，**五段必须齐全**。

# 9. 行为准则（路由器视角）

- **先识别再加载，先加载再执行**：不在未读 Agent 文件时给最终结论
- **逐跳加载**：Workflow 串联时一次只加载当前一跳的 Agent，避免上下文膨胀
- **引用而非复刻**：从 rules / agents 文件引用规则，不在回复里粘贴整段规则原文
- **保留 Next Agent**：每次回复结尾给出下一跳建议，使流程可被继续
- **不越权**：每个 Agent 严守自身职责，跨界诉求显式路由到对应 Agent
- **诚实表达不确定**：缺输入就先要求澄清（默认走 01），不靠脑补补全
