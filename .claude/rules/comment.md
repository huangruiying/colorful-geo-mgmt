# 通用代码注释规则

本文件是跨语言原则的唯一来源。Java 的必需注释见 [comment-java.md](comments/comment-java.md)，Python 见 [comment-python.md](comments/comment-python.md)；具体检查过程由 [代码变更流程](../workflows/code-change-flow.md) 执行。

## 1. 目标与优先级

- 一眼看懂代码承担的业务职责、主流程、决策依据与边界。
- 注释说明业务意图、数据来源、失败语义、兼容原因，不逐行翻译代码。
- 优先改善命名和结构，但不能用“代码已经易读”省略语言硬规则要求的类、方法、阶段和决策注释。
- 不设置注释比例上限。语言要求的必要注释不受文件长度或注释密度限制。
- 注释保持中文、准确、简明；复杂细节可以放在简短总述之后，不写大段示例业务代码。

## 2. 各层说明什么

| 位置 | 要说明的内容 |
|---|---|
| 文件 / 类 | 第一句直接说明是什么、管什么，再写职责、核心入口和不负责的边界；Java 可用类 Javadoc 承载，避免复制一份文件头，首句强制要求见 [comment-java.md](comments/comment-java.md) 1.1 |
| 方法 | 功能与业务目的、实际参数、返回和重要失败语义；详细要求以语言规则为准 |
| 业务阶段 | 当前阶段做什么、处理谁、数据来自哪里、失败后怎么办 |
| 业务决策 | 判断顺序、状态语义、成功或失败依据、未知值与兼容处理 |
| 生命周期 | 启动、运行、停止、资源归属和释放顺序 |
| 字段 | 不直观的业务含义、单位或状态职责；不翻译简单类型与赋值 |

“调用方法要注释”指被调用业务方法有职责说明，以及调用点按业务阶段解释目的；不是每个方法调用都加一条翻译式注释。

## 3. 必须说明的业务边界

业务规则、状态流转、外部响应解析、重试/限流、历史兼容、缓存策略、资源收尾、关键优化和特殊算法，应在发生判断的位置解释原因。
同一结论的一组条件共用说明，不把每个 if 都写成一段注释。

## 4. 同步与禁止事项

- 修改方法后检查整个方法的注释与阶段，而不只检查新增行。
- 修改职责、字段、状态或行为时同步修正相关注释；删除过时说明。
- 不为无关旧代码批量补注释；但本次修改方法内的失真或缺漏必须补齐。
- 不写翻译式、情绪化、含敏感信息或没有实际作用的注释。
- 不用注释掩盖不必要的抽象、混乱职责或未实现行为。
- 注释中的“已验证”必须有证据；源码实现不能写成真实平台联调成功。
