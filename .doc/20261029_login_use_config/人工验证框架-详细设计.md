# 【浏览器自动化】人工验证框架与预发布后台执行 - 详细设计

> 需求编号：待定。本文为设计稿，尚未开发；开发前以评审确认的版本为准。

# 需求背景

浏览器自动化（预发布、登录）在执行中会遇到平台的人机验证：滑块拼图、短信安全验证、图形验证码等。典型案例是搜狐号：新设备打开编辑器会跳到 `/mpfe/v4/clientAuth`，点“获取验证码”后弹出腾讯滑块（`turing.captcha.gtimg.com`）。部署到服务器后，出口 IP 和机器环境变化，这类验证大概率会再次出现。

现状有两个问题：

1. 遇到验证只能失败，用户无法在服务器上完成验证。
2. 批量预发布在一次 HTTP 请求里同步执行全部平台。中途若要等人工验证（可能几分钟），请求会被 Nginx 等代理按超时断开，页面关闭也会中断。

**核心语义：**

- 不识别验证码、不模拟拖动轨迹、不伪造或转交验证票据。验证一律由用户本人在平台的真实页面上完成。
- 自动化识别到验证 → 暂停当前平台、登记“待人工验证” → 管理页弹出“远程浏览器”窗口 → 用户在窗口里操作真实页面 → 验证页消失后自动继续。
- 超时或用户放弃 → 该平台记为失败并写明原因，不影响同批次其他平台。

**本方案目标：**

- 一套通用框架：识别规则、待验证队列、远程浏览器窗口、全局弹窗。预发布、登录及后续业务（如评论抓取）都能接入，新平台一般只需补一条识别规则。
- 预发布改为后台执行，提交后立即返回，页面轮询结果；部署后不再受请求超时影响。
- 分三期交付：一期后台执行；二期框架本体，以搜狐号试点；三期推广到其他平台和登录流程。

# 实现逻辑

## 整体逻辑

```Plain Text
提交预发布 ──> 插入发布记录（初始化）──> 立即返回
                         │
          预发布后台任务领取“初始化”记录，逐平台执行
                         │
    ┌────────────────────┼─────────────────────┐
  知乎：正常完成     搜狐号：识别到验证        哔哩哔哩：正常完成
                         │
            登记“待人工验证”，当前平台线程等待
                         │
   任意管理页的全局脚本轮询到待验证 → 弹出“远程浏览器”窗口
   画面：CDP Page.startScreencast 推帧；操作：Input.dispatch* 转发
                         │
     用户点按钮 / 拖滑块 / 填短信 ──> 验证页消失 ──> 继续存草稿
                         │
          超时 / 放弃 ──> 该平台记为失败（写明原因）
```

### 一期：预发布后台执行

- 提交接口只做校验、插入发布记录（状态“初始化”），立即返回当前记录列表。
- 预发布由同步改为异步：新增后台 Job `presentation/task/ContentPrePublishWorker`，与 `DiagnosisTaskWorker` 同包、同做法，使用 `ThreadPoolConfig` 中新增的专用线程池。
- Job 定时扫描状态为“初始化”（待发布）的发布记录；领取用带状态条件的更新（`WHERE status = 初始化` 改为“预发布中”），更新成功才算领到，保证同一条记录只执行一次。领到后调用平台策略，结果写回记录。执行顺序仍为逐平台串行。
- 服务重启时，遗留的“预发布中”记录保持原状态：该状态本身即表示“结果待核对”（与原同步执行时请求中断的结果一致），不自动重试，避免重复建稿。因此不需要诊断任务那样的数据库会话锁；防重复执行由领取时的条件更新保证，多实例同时领取也只有一个成功。
- 实现（2026-10-30 已完成一期）：`ContentPrePublishWorker`、`ThreadPoolConfig.prePublishTaskExecutor`（单线程）、`ContentPublishRecordService.claimNextInitializedRecord`（替代原 `startPrePublish`）、`ContentPublishBusiness.prePublish` 只建记录；页面轮询最长 15 分钟，超过视为待人工核对。
- 内容优化页、发布记录页对“初始化 / 预发布中”的记录定时轮询（3 秒），直到终态。

### 二期：人工验证框架

包：`infrastructure/client/playwright/verification/`（与 `PlaywrightBrowserComponent` 并列，只处理浏览器页面层面的技术细节，不认识投放、登录等业务）。识别规则、识别器、待验证队列、远程浏览器内聚在这一个包里；需要平台信息时引用公共枚举 `PublicationPlatformType`，只有用到通用工具类时才放到公共包。

| 组件 | 职责 |
|---|---|
| `HumanVerificationRule`（枚举） | 全部识别规则集中在此：通用验证码特征（腾讯 `turing.captcha`、极验 `geetest`、阿里云滑块 `nc_`、网易易盾 `dun.163` 等，按 iframe 地址、脚本、可见元素判断），以及平台专属规则（如搜狐号 URL 含 `/clientAuth`，规则上标明适用平台）。新增或调整识别只改这一处 |
| `HumanVerificationDetector` | 判断页面当前是否处于人工验证：通用规则 + 当前平台适用的专属规则 |
| `HumanVerificationRegistry` | 待验证登记表（Spring 单例，内存 Map）：登记页面、平台、业务（预发布 / 登录）、原因、开始时间、期限；提供查询、取画面、转发操作、放弃；按序排队。放在本包而非 common：Map 中持有 Playwright `Page`，依赖浏览器技术，且只服务本套流程 |
| `RemoteBrowserSession` | 远程浏览器：对登记页面开启 CDP 会话，`Page.startScreencast` 推送画面帧；把前端的鼠标、滚轮、键盘事件转成 `Input.dispatchMouseEvent` / `Input.insertText` 等发回页面 |
| 入口方法 `ensureHumanVerified(page, platform)` | 策略在关键步骤调用：未识别到验证直接返回；识别到则登记并阻塞等待，结局为“已通过 / 超时 / 已放弃”。策略不自带识别规则 |

平台客户端的接入方式（以搜狐号为例）：把现在遇到 `/clientAuth` 就抛异常，改为调用 `ensureHumanVerified`。通过后继续存草稿；超时或放弃时抛出现有的 `PublicationClientException`，原因写入发布记录。

前端：`static/admin/shared/human-verification.js`，由所有管理页引入（同 `navigation.js`）。轮询待验证列表，有记录时弹出窗口：标题写明平台和业务，中间是实时画面（`<canvas>`），提供“放弃”按钮；一次只展示一条，处理完自动切到下一条。

### 二期交互流程

**原则：平时不推画面，识别到验证后才推；页面始终主动去拉，服务器不主动推送。**

#### 1. 待验证登记表

`HumanVerificationRegistry` 是 Spring 单例，整个进程只有一份，内部为线程安全 Map：

```Plain Text
待验证 ID（随机 UUID） → 待验证记录
                          ├─ 平台、业务（预发布 / 登录）、原因、开始时间、截止时间
                          ├─ Playwright Page（服务器上停在验证页的那个页面）
                          ├─ 最新一帧画面（开始推送后才有，只保留最新一帧）
                          └─ 完成信号（CompletableFuture：通过 / 放弃 / 超时）
```

后台任务线程与 HTTP 请求线程在同一个 Java 进程里，注入的是同一个单例，因此无需数据库、Redis 或其他缓存来传递“需要展示”的消息。

#### 2. 完整流程

| 步骤 | 执行方 | 动作 |
|---|---|---|
| 1. 识别 | 后台任务线程（如预发布 Job） | 执行到 `ensureHumanVerified(page, 平台)`，`HumanVerificationDetector` 按 `HumanVerificationRule` 判断页面处于验证；未识别到则直接继续，不产生任何开销 |
| 2. 登记并等待 | 后台任务线程 | `registry.register(...)` 生成 UUID、写入 Map，然后在完成信号上等待，最长 10 分钟。此时仍不截图、不推画面 |
| 3. 发现 | 任意管理页的公共脚本 `shared/human-verification.js` | 每隔几秒 `GET /human-verifications`；Controller 注入同一个 registry，直接读 Map 返回。有记录即弹出窗口（一次一条，按登记顺序） |
| 4. 开始推画面 | 弹窗 → 服务器 | 窗口首次 `GET /human-verifications/{id}/frame` 时，服务器才对该 Page 开启 CDP `Page.startScreencast`；页面每变化一次产生一帧，记录中只保留最新一帧 |
| 5. 显示画面 | 弹窗 | 约每 150ms 拉取一次最新帧，按 `sequence` 跳过旧帧，绘制到窗口的 `<canvas>` 上 |
| 6. 用户操作 | 弹窗 → 服务器 | 每个点击、拖动、滚轮、输入单独 `POST /human-verifications/{id}/input`；服务器按 UUID 取出 Page，用 CDP `Input.dispatchMouseEvent` / `Input.insertText` 等作用在真实页面 |
| 7. 判断通过 | 服务器 | 每次取帧时顺带用同一套规则再识别一次；验证页消失则完成信号置为“通过”，停止推送并从 Map 删除 |
| 8. 结束 | 弹窗 / 后台任务线程 | 弹窗下次取帧收到 `resolved: true` 后关闭；后台任务线程被唤醒，继续执行（如存草稿） |

#### 3. 其他结局

- **放弃**：弹窗点“放弃” → `POST /human-verifications/{id}/abandon` → 完成信号置为“放弃”，停止推送、删除记录，该平台记为失败（原因“已放弃人工验证”）。
- **超时**：10 分钟未完成 → 完成信号超时，处理同“放弃”，原因“等待人工验证超时”。
- **窗口关闭但未放弃**：停止取帧后服务器停止截图；记录继续排队，再次打开任意管理页会重新弹出，直到通过、放弃或超时。
- **无人打开管理页**：记录在 Map 中排队等待，超时后失败；同批次其他平台不受影响。

#### 4. 为什么只放内存

记录中最关键的是正在运行的浏览器 Page，只能存在于当前 Java 进程，无法序列化到数据库或 Redis。代价：

- 服务重启：Map 清空，对应浏览器也随进程关闭，相关平台按“结果待核对”处理。
- 多实例部署：请求可能落到没有该浏览器的实例，需另做请求路由；当前为单实例部署，不受影响。

### 三期：推广

- 其余预发布客户端在打开编辑器、保存后等关键步骤接入 `ensureHumanVerified`。

# 接口文档

## 接口基础信息

### 提供接口的服务

colorful-geo-mgmt 管理后台（需登录，写请求带 `X-XSRF-TOKEN`，前端统一走 `AdminHttp.requestJson`）

### 服务域名

与管理后台同域。

## 接口一：提交预发布（语义变更）

接口地址：POST /content-publish/{id}/pre-publish（现有路径，不改）

**Request**

无新增字段。

**Response**

无新增字段。返回时各平台记录为“初始化”或“预发布中”，不再等待平台结果；页面需轮询发布记录直到终态。

## 接口二：待人工验证列表

接口地址：GET /human-verifications

**Request**

无。

**Response**

```JSON
[
  {
    "verificationId": "c6f2…",
    "platformType": "SOHU",
    "platformDisplayName": "搜狐号",
    "business": "PRE_PUBLISH",
    "reason": "搜狐号要求短信安全验证",
    "startedAt": "2026-10-30T10:00:00",
    "expiresAt": "2026-10-30T10:10:00"
  }
]
```

字段说明：`verificationId` 待验证记录标识（随机串，非数据库 ID）；`business` 取值 `PRE_PUBLISH` / `LOGIN`；`expiresAt` 超时时间，到期后该平台记为失败。

## 接口三：远程浏览器画面

接口地址：GET /human-verifications/{verificationId}/frame

**Request**

无。

**Response**

```JSON
{
  "imageBase64": "…",
  "width": 1280,
  "height": 900,
  "sequence": 128,
  "resolved": false
}
```

字段说明：`sequence` 帧序号，前端用来跳过旧帧；`resolved` 为 true 表示验证已通过，前端关闭窗口。传输方式先用短轮询（约 150ms，已确认），实测延迟不够时再改 WebSocket。

## 接口四：转发操作

接口地址：POST /human-verifications/{verificationId}/input

**Request**

```JSON
{
  "type": "mouseMoved",
  "x": 512,
  "y": 380,
  "button": "left",
  "text": null
}
```

字段说明：`type` 取值 `mousePressed` / `mouseMoved` / `mouseReleased` / `mouseWheel` / `insertText` / `keyDown` / `keyUp`；`x`、`y` 为画面坐标（前端按窗口缩放换算回页面坐标）；`text` 仅 `insertText` 使用。只转发到该记录对应的页面。

**Response**

204，无正文。

## 接口五：放弃验证

接口地址：POST /human-verifications/{verificationId}/abandon

**Request**

无。

**Response**

204。该平台立即结束等待并记为失败，原因“已放弃人工验证”。

# 发版影响分析

### 阶段一：一期代码上线，后台任务开启

预发布提交即返回，页面轮询结果；平台调用逻辑不变。
DB：无变更。Redis：不涉及。
影响：提交后页面先显示“预发布中”，结果需等轮询刷新；服务重启时正在执行的平台按“结果待核对”处理，与现状一致。

### 阶段二：二期代码上线，仅搜狐号接入

搜狐号遇到 `/clientAuth` 时等待人工验证；其他平台行为不变。
DB：无变更。Redis：不涉及。
影响：无人处理时，搜狐号等待最长 10 分钟后失败，期间同批次其他平台照常执行；一个后台线程会被占用到超时。

### 阶段三：其他平台、登录流程逐步接入

按平台逐个接入识别调用。
DB：无变更。Redis：不涉及。
影响：接入的平台遇到验证时由“直接失败”变为“等待人工验证”；未接入的平台不变。

# 灰度顺序

1. 上线一期，在测试账号上提交多平台预发布。验证：提交立即返回，页面状态从“预发布中”变为终态，发布记录与平台草稿一致。
2. 观察一期运行，确认无重复建稿、无记录卡在“初始化”。验证：日志中每条记录只被领取一次。
3. 上线二期，搜狐号使用新部署服务器的登录态预发布。验证：出现待验证弹窗，远程画面清晰，可在窗口中完成滑块和短信。
4. 实测放弃和超时。验证：搜狐号记录为失败并写明原因，其他平台正常完成。
5. 逐个平台接入三期识别规则。验证：各平台遇到验证时弹窗出现，未遇到时无额外等待。

# 测试关注点

- 提交多平台预发布，是否立即返回，且每条记录最终进入终态
- 服务在“预发布中”时重启，是否标记为待核对且不自动重新建稿
- 后台任务开关关闭时，提交的记录是否停在“初始化”且不调用平台
- 页面未遇到验证时，`ensureHumanVerified` 是否不产生额外等待
- 搜狐号跳转 `/clientAuth` 时，是否登记待验证并在任意管理页弹窗
- 远程窗口中点击、拖动、输入，是否作用在服务器页面的对应位置（含窗口缩放换算）
- 验证通过后是否自动关闭窗口并继续存草稿
- 超时、放弃后，该平台是否记为失败且原因可读，同批次其他平台是否不受影响
- 多条待验证是否按顺序逐条弹出
- 画面帧、操作事件是否不写入日志，接口是否要求管理员登录与跨站令牌
