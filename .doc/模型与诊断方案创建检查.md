## 发现

### 中：模型配置项保存了，但实际调用不使用

- model-config.html:83 仍要求填写渠道请求超时，models.js:54/57 仍提交渠道 timeoutSeconds/sslVerify。两个协议模板已改为注入固定 llmRestTemplateWithTimeout，实际采用 application.yml 的 http.llm；渠道字段不再影响 HTTP。
- AbstractResponsesApiStrategy.java:72 的请求体只发送 model/input/store，子策略只追加工具，未发送页面 temperature/maxTokens。OpenAI Chat 搜索模型也明确移除普通生成参数。页面却把随机性和 token 上限作为所有策略通用必填项。

建议：先清理渠道中已经不生效的 HTTP 配置页面入口及后台字段，再按实际策略支持情况显示和发送生成参数。不能把 Chat 的 max_tokens 直接复制到 Responses；厂商、模型不支持时应明确不适用。

### 低：超时错误提示仍指向无效配置

MgmtDiagnosisPlanController.generationFailed 建议“检查渠道超时配置”，但当前统一超时由 YAML 管理。应同步为“检查统一 HTTP 超时配置”。连接池获取连接超时等异常也尚未细分，可能显示通用失败提示；未进行本轮异常 HTTP 联调。

### 低：方案关联校验尚未检查实际调用策略

GeoDiagnosisPlanService.java:84 仅确认被测渠道存在且启用，不检查其 Bean 是否仍注册或远程密钥是否有效。渠道最初保存/启用和调用路由已有校验，但删除策略后旧启用配置仍可能被保存到方案。

建议：仅检查当前 Bean 存在和必要的本地配置，不在保存方案时调用所有外部模型；真正执行前再次校验并冻结配置。此项是代码边界风险，不代表现有六个渠道已经失效。

## 当前实现边界

- 每次生成最多 30 个候选（QuestionGenerateService.java:32），方案最多 200 个。100 个问题需要多次生成后加入，不是分页显示故障。
- 方案创建只保存配置和问题；执行记录/结果目前只有存储结构，没有完整执行、调度和报告链路。保存成功不等于开始诊断。
- 方案问题重复、非法品牌标记、渠道重复及停用、无效项目、重复次数范围都有源码校验；三张表保存同一事务，编辑先锁定方案，失败回滚。
- 页面候选不自动保存、查看只读、采样预估采用问题数×勾选渠道数×重复次数、保存成功关闭弹窗的逻辑仍存在。本轮未以浏览器或真实数据库创建新方案复验。
