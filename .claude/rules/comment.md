# 代码注释规范（Comment Specification）

## 1. 目标

注释的核心目标：一眼看懂干啥

- 突出核心流程、步骤，像简洁的操作手册
- 复杂注释可以先总的概括，然后在()中加上详细描述
- 解释业务意图，一句话，核心，直观，易懂
- 解释设计原因，可以写在详细描述中
- 解释边界条件，可以写在详细描述中
- 解释特殊处理逻辑，可以写在详细描述中
- 降低维护成本

注意：注释不应重复代码字面含义。
注意：注释和日志都该聚焦业务关键点（监听了什么地址、按什么过滤、值取到哪个变量），而不是描述 代码的 机制（finally 怎么访问变量、gather
的异常语义、防御性兜底）。

## [最优先]严格按照 `comments` 文件夹下的注释要求

## 2. 核心结构

"埋点 → 命中 → 取值 → 入袋"四步

---

# 2. 核心原则

## 2.1 关键步骤注释: 识别关键步骤，加入关键注释

关键步骤日志 ，可以使用 「===== 1. xxxxx =====」进行突出

---

## 2.2 要能够通过代码表达含义

应优先优化：

* 变量命名
* 函数命名
* 模块拆分

而不是依赖大量注释。注释按我提供的正确示例，分核心流程 + 关键细节

---

## 2.3 注释必须与代码同步

修改代码逻辑时：

* 必须同步更新注释
* 删除无效注释
* 禁止保留历史错误描述

---

## 2.4 类、文件注释要简明扼要

类、文件代码背景

* 阐述做了类、文件
* 核心对外提供服务的是哪几个方法
* 直观的方法调用链与方法作用(尽量10个字描述清楚)

---

# 3. ** 重点：注释层级规范 **

## 3.1 文件级注释

用于说明：

* 模块职责
* 核心流程
* 使用限制

---

## 3.2 类级注释

用于说明：

* 核心抽象
* 使用场景
* 生命周期

---

## 3.3 方法级注释

用于说明：

* 功能
* 参数
* 返回值
* 副作用
* 注意事项

---

## 3.4 方法内注释

* 调用的方法必须要加注释
* 用换行分开的复杂逻辑，加一个总注释

* 特殊业务逻辑
* 边界处理
* 兼容方案


---

## 3.5 行级注释

仅允许用于：

* 位运算
* 数学公式
* 特殊Hack
* 极难理解逻辑

### 示例

```python
# 使用位运算快速判断是否为2的幂
is_power_of_two = n > 0 and (n & (n - 1)) == 0
```

---

# 4. 必须添加注释的场景

以下场景必须添加注释：

* 业务规则
* 魔法值
* 状态机
* 缓存策略
* 并发控制
* 重试机制
* 限流逻辑
* 风控逻辑
* 正则表达式
* 性能优化
* 第三方兼容
* 历史遗留兼容
* 临时Hack方案

---

# 5. 禁止注释的场景

## 5.1 禁止翻译代码

### 错误示例

```python
# 设置名字
name = "test"
```

---

## 5.2 禁止废话注释

### 错误示例

```python
# 判断是否为空
if value is None:
```

---

## 5.3 禁止情绪化注释

### 错误示例

```python
# 这里太恶心了
# 不知道谁写的
```

---

## 5.4 禁止过时注释

注释与实际逻辑不一致时：

* 必须立即更新
* 或直接删除

---

# 6. AI 注释生成规范

## [最优先]严格按照 `comments` 文件夹下的注释要求
- java: comment-java.md
- python: comment-python.md

## 6.1 AI 应优先解释

* 业务目的
* 输入输出约束
* 边界条件
* 副作用
* 设计原因
* 为什么采用当前方案

---

## 6.2 AI 禁止生成

* 翻译式注释
* 无意义注释
* 猜测性描述
* 与代码不一致内容
* 无依据业务推测

---

## 6.3 AI 注释生成原则

AI 生成注释时：

* 优先解释意图
* 避免重复代码
* 保持简洁
* 保持一致风格

---

# 7. 特殊标记规范

统一使用以下标签：

| 标签       | 含义    |
|----------|-------|
| TODO     | 后续待完成 |
| FIXME    | 已知问题  |
| HACK     | 临时方案  |
| NOTE     | 重要说明  |
| WARNING  | 高风险逻辑 |
| OPTIMIZE | 待优化   |

---

## 示例

```python
# TODO: 后续改为异步处理
```

```python
# FIXME: 第三方接口偶发超时
```

```python
# HACK: 临时兼容旧版客户端
```

---

# 8. 注释密度规范

## 原则

* 注释密度建议不超过代码量的 20%~30%
* 优先优化代码可读性
* 避免大段无意义注释

---

# 9. Review 检查项

Code Review 时必须检查：

* 注释是否失效
* 是否存在废话注释
* 是否遗漏关键业务说明
* 是否存在误导性描述
* AI 生成内容是否准确

---

# 10. 注释生命周期

## 责任归属

代码修改人：

* 必须维护对应注释
* 保证注释准确性

---

## 注释删除原则

以下情况应删除注释：

* 注释已失效
* 代码已足够清晰
* 注释仅重复代码
* 历史兼容逻辑已移除

---

# 11. 最终原则

优秀注释应：

* 解释意图
* 解释原因
* 解释限制
