# Workflow D —— 技债治理链（tech-debt）

> 代码实现、适用规则加载、逐方法注释审计和架构验收统一执行 [代码变更流程](code-change-flow.md)。本文件只维护本专题的前后阶段，不复制公共验收标准；按当前阶段逐个加载角色，角色链不要求创建多代理。

> 适用场景：重复出现的问题 / 路标前体检 / 模块迁移前评估 —— 把"技债识别 → 三类整改 → PR 摘要"打成一条链。
>
> 触发关键词："技债 / 治理 / 路标体检 / 重复 bug / 这块要重写 / 升一下依赖"
>
> 核心原则：**20 入口识别债项 → 按债类型并发整改 → 代码整改默认补单元测试并评审 → 21 PR 摘要收尾**，每条债先建条目再落手。

---

## 1. 串联顺序

```text
20 tech-debt                  债项识别
    ├─→ 05 refactor           代码重构
    │      ↓
    │    06 unit-test-gen     默认补单测
    │      ↓
    │    09 code-review       代码整改验收
    ├─→ 11 dependency-audit   依赖审计
    └─→ 02 architecture-review 架构评审
    ↓
21 pr-summary                 PR 摘要
```

---

## 2. 阶段定义

| 阶段 | Agent             | 目标                                | 验收                          |
|----|-------------------|-----------------------------------|-----------------------------|
| 20 | tech-debt          | 识别具体债项 / 影响 / 整改优先级                | 出"债项清单 + 优先级 + 责任人"           |
| 05 | refactor           | 代码层债：方法过长 / 命名混乱 / 抽象错误            | 主流程像操作手册，命名表达业务语义              |
| 06 | unit-test-gen      | 代码整改后默认补关键行为回归单测                    | 能运行则测试通过；不能运行则明确记录原因          |
| 09 | code-review        | 代码整改分支收口评审                               | 无 CRITICAL/HIGH 阻塞问题                     |
| 11 | dependency-audit   | 依赖层债：CVE / License / 严重过期版本         | 升级清单 + 不能升级的原因               |
| 02 | architecture-review | 架构层债：分层混乱 / 模块边界 / 循环依赖             | 出"分层评估 + 可演进路线"               |
| 21 | pr-summary         | 把本次治理的范围 / 取舍 / 测试结果写清楚              | 摘要可直接合入 PR 描述                |

05 / 11 / 02 之间**按债类型并发**，不是必须三条全跑；但只要执行 05，就必须继续走 06 → 09。

---

## 3. 输出契约

按 workflow.md 报告结果、证据和限制。**Findings 段每条债项必须含"代价估算 + 不治理的后果"**。

---

## 4. 严守边界

- **不做新功能**：D 是治理已有代码，新功能走 A
- **不做安全扫描**：跨界路由 B；但 11 与 B 中的 11 一致，避免重复
- **不修无人确认的债**：必须 20 出清单后才动手，禁止顺手"改一个发现的小问题"
- **代码整改默认补测**：05 产生代码改动后必须补 06，再由 09 验收
- **风险升级**：改写已发布行为 → 必加 25 ADR；动接口语义 → 必加 03 接口设计

---

## 5. 触发示例

```text
"这个模块代码屎山了，治理一下"     → D
"路标前做次体检"                  → D
"我们要重构掉这套老接口"           → D
```

## 6. 与其他 Workflow 的关系

| 关系             | 说明                                              |
|----------------|-------------------------------------------------|
| 与 Workflow A 区别 | A 是新功能；D 是治理已有代码                               |
| 与 Workflow E 区别 | E 是单文件 / 小范围"重构收尾"；D 是模块级 / 跨文件的"治理"           |
| 与 05-refactor   | 05 是 D 的核心整改 agent；05 单跑只做一次重构动作，D 把它放进治理链路    |
