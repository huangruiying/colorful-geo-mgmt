# 管理后台多账号与浏览器人工接管隔离 - 方案记录

> 记录时间：2026-11-01。状态：已讨论，暂不开发。动手前先核对当前代码；正式开发时按 `.claude/rules/tech-design-doc.md` 补成详细设计。

## 背景

浏览器人工接管的待接管记录在服务器上全局唯一，所有打开着的管理页都能看到、都能操作同一条接管：

- 两个窗口同时操作，动作会混进同一个队列，回放时间线也会混在一起；
- 任一窗口点“放弃接管”，所有窗口一起结束；
- 每个打开的窗口都在取画面，带宽成倍消耗，服务器 1M 带宽下尤其明显。

用户提出：做多账号，哪个账号发起的操作，哪个账号才能获取对应的接管。

## 记录时的现状

- **登录**：只有一个管理员账号。`AdminSecurityConfig` 用 `InMemoryUserDetailsManager`，账号来自 `admin.login.username`、`admin.login.password-hash`（环境变量 `GEO_ADMIN_USERNAME`、`GEO_ADMIN_PASSWORD_HASH`），不建用户表；同一 IP 连续失败 5 次锁定 15 分钟（`LoginAttemptLimiter`）。
- **默认密码**：`application.yml` 给 `admin.login.password-hash` 写了默认哈希，注释里还有生成它的明文密码。不设环境变量也能启动，与“未配置哈希时服务拒绝启动”的约定不符。
- **数据**：所有表都没有创建人字段，数据不区分账号。
- **平台登录态**：`platform_browser_login` 按 `platform_type` 唯一，每个平台全系统只有一份。搜狐号等平台的短信验证码只发到该平台账号绑定的手机。
- **预发布链路**：提交时插入 `content_publish_record`（没有发起人）→ 后台 `ContentPrePublishWorker` 单线程领取 → `ContentPublicationService` → 平台策略 → 平台客户端（如 `SohuBrowserClient`）→ `HumanVerificationTakeover.ensureHumanVerified` → `BrowserTakeoverRegistry.requestTakeover(页面, 标题, 原因, 完成条件)`。接管由后台线程发起，不挂在任何人的请求上。
- **接管接口**：`/browser-takeovers` 不区分账号。

## 讨论结论

1. **身份只能从登录会话取，接口不接收 userid。** 页面传的值用户自己能改，改成别人的 ID 就能看到、操作别人的接管。服务端从 Spring Security 的当前登录人取身份，前端请求不用改。
2. **接管与发起人绑定（2026-11-01 用户确认）。** 用户只能看到、操作自己发起的接管，不同的人碰不到同一条接管。为此发布记录要记下发起人，后台任务执行时再传给接管。
3. **不做窗口操作权（2026-11-01 用户确认）。** 同一个账号开多个窗口仍共用同一条接管，但同一个人一次只操作一个窗口，不会真正冲突。只补“标签页切到后台就停止取画面”，避免多个窗口重复占用带宽。
4. **平台登录态全系统一份。** 搜狐的短信只发到绑定的手机，能完成验证的是拿着手机的人，不一定是发起人。平台账号要不要按人分开，需要先定。

## 方案要点

### 1. 账号与登录

- 新建管理员账号表，表名按项目约定带模块前缀（如 `geo_admin_user`）：用户名（唯一）、BCrypt 密码哈希、启用状态、创建时间；不存明文密码。
- Spring Security 改为从数据库加载用户，替换 `InMemoryUserDetailsManager`；保留现有登录页、跨站令牌和登录锁定。
- 初始账号：首次启动且账号表为空时，用环境变量创建第一个账号；去掉 `application.yml` 里的默认密码哈希和明文注释。
- 账号管理页：新增、停用、重置密码。
- 用用户 ID 作身份标识：用户名可能改，ID 不变。

### 2. 发起人

- `content_publish_record` 增加发起人（用户 ID，可空）。`ContentPublishBusiness.prePublish` 插入记录时从登录会话取；历史记录为空。
- 后台任务执行记录时把发起人带到接管登记，两种传法，开发时选定：
  - **显式参数**：`PublicationRequest` → `PlatformPublicationRequest` → 平台客户端 → `ensureHumanVerified` → `requestTakeover` 逐层加参数。链路清楚，但用到接管的客户端都要改。
  - **线程上下文**：Worker 处理每条记录前，把发起人放进当前线程的上下文，处理完清除；`requestTakeover` 从上下文读取。改动小，但依赖“接管在 Worker 线程里发起”这一隐含前提（现状正是如此）。

### 3. 接管分派

- 接管记录增加“处理人”（用户 ID），即发起人。框架只把它当不透明标识，不认识业务。
- `GET /browser-takeovers` 只返回当前登录人发起的接管。画面、操作、放弃接口校验处理人，不是处理人的一律返回 404，与“已结束”同样处理，不暴露接管是否存在。
- 没有发起人的接管（升级前已在排队的记录、以后的定时任务）按此规则谁都看不到，只能等超时，需要兜底规则，见待定决策。

### 4. 同一账号开多个窗口

- 不做窗口操作权（2026-11-01 用户确认）：同一个人一次只操作一个窗口，各窗口的操作不会同时到达。
- 只补一项：标签页切到后台时停止取画面，切回来恢复。现在窗口打开后即使切到后台也在取画面（浏览器降到约每秒一次），多开几个窗口会重复占用带宽。这项不依赖多账号，随带宽优化一起做。
- 留作参考：如果出现多人共用一个账号，再考虑窗口操作权，即同一条接管同一时间只接受一个窗口的操作，其他窗口只显示“正在其他窗口处理”。

## 待定决策（开发前确认）

1. **数据是否按账号隔离**：建议先做“共享数据、多人登录”，团队共用一个工作台，账号只用于登录、审计和接管分派。按账号隔离数据要改所有表和查询，确有需求再做。
2. **平台登录态是否按账号分开**：与 [TODO.md](TODO.md) 中“同一平台需要多个账号”一起定。接管交给发起人后，发起人要能完成平台验证；平台账号共用时，短信可能发到别人的手机上。
3. **是否区分角色**：谁能管理账号、模型配置和平台登录。
4. **没有发起人的接管谁能处理**：建议所有账号可见，或指定一个默认处理人。
5. **发起人的传法**：显式参数还是线程上下文。

## 影响范围（记录时）

| 位置 | 改动 |
|---|---|
| 数据库 | 新增账号表；`content_publish_record` 增加发起人 |
| `infrastructure/config/security/AdminSecurityConfig` | 改为从数据库加载用户；创建初始账号 |
| `application.yml` | `admin.login.*` 只用于初始账号；删除默认密码哈希和明文注释 |
| `ContentPublishBusiness.prePublish` | 写入发起人 |
| `ContentPrePublishWorker` 至 `BrowserTakeoverRegistry` | 传递发起人（见上） |
| `BrowserTakeoverRegistry`、`MgmtBrowserTakeoverController` | 接管带处理人；接口按处理人过滤和校验 |
| 前端 | 新增账号管理页和导航入口；接管窗口不需要传 userid |
| `.claude/rules/project-conventions.md` | 方案确认后，修改“登录与访问控制”中“只有一个登录账号、不建用户表” |

## 建议顺序

1. 账号表与登录。
2. 发起人与接管分派。
3. 账号管理页面。

“切到后台停止取画面”不依赖以上步骤，随带宽优化一起做。
