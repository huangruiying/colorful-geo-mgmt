# Workflow A —— 功能交付链（feature-delivery）

> 代码实现、适用规则加载、逐方法注释审计和架构验收统一执行 [代码变更流程](code-change-flow.md)。本文件只维护本专题的前后阶段，不复制公共验收标准；按当前阶段逐个加载角色，角色链不要求创建多代理。

> 适用场景：新需求 / Story / 新功能 —— 从需求拆解到 PR 摘要的完整交付链。
>
> 触发关键词："加个 X 功能 / 想做 X / 新需求 / 实现 X / 新增接口 / 接口文档"
>
> 核心原则：**先理解再实现 → 实现后默认补单元测试 → 再评审 → 全量测试诉求再进真实接口回归 → PR 摘要**，每跳逐个加载，不一次性吞 Agent。

---

## 1. 串联顺序

```text
01 requirements-breakdown    需求拆解
    ↓
03 api-contract-design       接口契约
    ↓
04 code-generation           代码生成
    ↓
06 unit-test-gen             单测（默认执行，不询问）
    ↓
09 code-review               代码评审
    ↓
如用户要求全量测试 → 31 runtime-api-test
    ↓
21 pr-summary                PR 摘要
```

---

## 2. 阶段定义

| 阶段 | Agent             | 目标                                 | 验收                       |
|----|-------------------|------------------------------------|--------------------------|
| 01 | requirements-breakdown | 把模糊需求拆成可实现条目，澄清未知                  | 输出"用户故事 + 接受标准"          |
| 03 | api-contract-design   | 定接口签名 / 错误码 / 字段 / 兼容性             | 输出"接口契约 + 字段语义"；需交付独立接口文档时遵守 `rules/api-doc.md` |
| 04 | code-generation       | 按契约写实现，引用专题 rules 写代码 / 命名 / 日志    | 主流程像操作手册，单方法 ≤ 30 行      |
| 06 | unit-test-gen         | 行为级单测，覆盖正常 / 边界 / 异常               | 默认执行；`pytest -q` 全过或明确记录无法执行原因 |
| 09 | code-review           | 按 09-code-review 清单逐项过                    | 无 CRITICAL/HIGH，LOW 有处置说明 |
| 31 | runtime-api-test      | 仅全量测试 / 真实接口回归诉求时执行真实请求、日志归因、重启回归、报告落地 | `.test/*_测试报告.md` 记录结果     |
| 21 | pr-summary            | 写"为什么 + 改了什么 + 怎么测"，关联 ADR / 缺陷单    | 摘要可直接合入 PR 描述            |

## 3. 输出契约

按 workflow.md 报告结果、证据和限制。

---

## 4. 严守边界

- **不做安全 / 性能 / 架构层评审**：跨界诉求路由 08 / 10 / 12 / 02
- **不省略 06**：04 与 06 强绑定，行为级单测是"敢合入"的下限
- **不跳过 09**：04/06 输出后必接 09，不允许直接到 21
- **31 只做全量回归**：09 后只有用户明确要求全量测试、真实接口回归、测试报告时，才加载 `workflows/runtime-api-test-flow.md`
- **风险升级**：涉用户输入入口 → 加 10；涉鉴权 / 密钥 → 加 26 + 08；引入新依赖 → 加 11


## 6. 与其他 Workflow 的关系

| 关系             | 说明                                            |
|----------------|-----------------------------------------------|
| 与 Workflow D 区别 | D 是已有代码的"治理"；A 是从 0 到 1 的"实现"               |
| 与 Workflow E 区别 | E 是初稿后的"重构收尾"；A 是完整功能链路（含需求 / 接口 / 测试 / 摘要） |
| 与 Workflow F 关系 | F 是全量 / 真实服务接口回归链；A 默认只跑到 06 + 09，明确要求全量测试时再进入 F |
| 与 09-code-review | 09 是 A 的强制收口节点，不能跳过                       |
