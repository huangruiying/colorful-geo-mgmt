# Workflow E —— 重构收尾五段链（refactor-finalize）

> 代码实现、适用规则加载、逐方法注释审计和架构验收统一执行 [代码变更流程](code-change-flow.md)。本文件只维护本专题的前后阶段，不复制公共验收标准；按当前阶段逐个加载角色，角色链不要求创建多代理。

> 适用场景：单文件 / 小范围已经完成"加注释 + 整结构"的初稿后，要把改动收尾到"可合入"水位。
>
> 触发关键词："重构收尾 / refactor-finalize / 这个文件改完后顺手做完它 / 把这套都执行了"
>
> 核心原则：**逻辑零改动 → 结构合并 → 横向铺开 → 默认补单元测试 → 统一 review**，阶段顺序不可调换。

---

## 1. 串联顺序

```text
P1 消 IDE 警告
    ↓
P2 抽方法合并
    ↓
P3 横向铺开
    ↓
P4 06-unit-test-gen
    ↓
P5 09-code-review
    ↓
P6 固化（仅本 workflow 自身首跑时做一次）
```

---

## 2. 阶段定义

### P1 消 IDE 警告

**目标**：在干净基线上做后续改动，避免噪音淹没真改动。

**动作**：
- PEP 604 联合类型（`X | Y`）若 IDE 误报，统一改 `Optional[X]` / `Union[X, Y]`
- 未用 `self` 的实例方法标 `@staticmethod`
- 任何"行为零变更"的诊断告警优先做掉

**验收**：`mcp__ide__getDiagnostics` 返回 `diagnostics: []`（或仅剩与改动无关的告警）。

---

### P2 抽方法合并

**目标**：消除 P0 / P1 之后留下的结构重复。

**动作**：
- 同形态注册 / 校验 / 分发逻辑提一个私有方法，公开 API 签名保留
- 引入"映射函数"（如 `_subscription_bucket(kind)`）收敛 if/elif 链
- 对**抛错**与**静默**的语义差异要显式注释（哪条路径严格，哪条路径宽容）

**验收**：
- AST 解析通过：`python -c "import ast; ast.parse(open(<file>).read())"`
- 单元测试全过（若有）：`python -m pytest <test_file> -q`
- 公开 API 签名 0 变更（grep 调用方确认）

---

### P3 横向铺开

**目标**：把主文件确立的"加注释 + 分块"风格推广到同主题兄弟文件，避免风格漂移。

**动作**：
- 同目录 / 同主题文件套用统一 docstring 模板（"做什么 / 关键概念 / 时序 / 排查"四段）
- 主流程阶段注释按 `rules/comments/comment-python.md` 执行；普通业务主流程用 `# 1. xxx`，生命周期/收尾流程才用 `# ===== 1. xxx =====`
- 关键不变量加 `Why:` 注释，不翻译代码字面

**验收**：
- 只动注释 / 顺序 / 空行，**不动逻辑、字段、签名、日志**
- AST 解析全部通过

---

### P4 06-unit-test-gen

**目标**：为本次结构性改动补齐回归单测，避免重构后行为漂移。

**动作**：
- 加载 `.claude/agents/builders/06-unit-test-gen.md`
- 按 `rules/testing.md` 补关键行为、边界、异常路径
- 无法运行单测时，必须明确记录原因和缺口

**验收**：
- 关键改动点有对应单测或明确记录无法补测原因
- 能运行时执行对应测试命令通过

---

### P5 09-code-review

**目标**：所有改动一起过一次 review，避免来回多次复核。

**动作**：
- 加载 `.claude/agents/guardians/09-code-review.md`
- 按其第 5 节清单逐项核（可读性 / 命名 / 注释 / 日志 / 异常 / 测试）
- 按 workflow.md 报告结果、证据和限制，并附代码变更流程的验收记录

**验收**：无 CRITICAL / HIGH 级 Risk；LOW 级风险全部有"修复建议或为什么不修"的明确说明。

---

### P6 固化（一次性）

**目标**：把本 workflow 写进 `.claude/`，下次自动可被路由命中。

**仅在首次运行本 workflow 时做**，后续触发同场景时跳过 P6。

---

## 3. 输出契约

每个阶段执行完打印一行进度条：

```text
P{n} {阶段名} ✅ / ❌（含原因）
```

最终回复必须包含结果、验证和限制；代码验收按 code-change-flow.md 执行。

---

## 4. 严守边界

- **不做架构调整**：抽方法仅限"内部合并"，不引入新模块、不改职责边界
- **不做安全 / 性能 / 漏洞扫描**：跨界诉求路由到 08 / 10 / 11 / 12
- **不做新功能**：本 workflow 只用于"把已写代码收尾到可合入"，新功能走 Workflow A

---

## 6. 与其他 Workflow 的关系

| 关系             | 说明                                               |
|----------------|--------------------------------------------------|
| 与 Workflow A 区别 | A 是"从 0 到 1 实现新功能"；本 workflow 是"已有代码的收尾"          |
| 与 Workflow D 区别 | D 是"识别技债 + 治理"，可能涉及大范围重构；本 workflow 限单文件 / 小范围收尾 |
| 与 05-refactor   | 本 workflow 是 05 的"标准跑法"；05 单独跑只做 P2 一段           |
| 与 09-code-review | 本 workflow 在 P5 必接 09，等价于"重构 + 自动接 review"       |
