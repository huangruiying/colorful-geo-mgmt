# 诊断方案

## 执行数据存储

新增 `geo_diagnosis_task` 保存方案的一次执行及非敏感配置快照；新增 `geo_diagnosis_task_result` 保存每个问题、渠道、重复序号对应的独立响应。结果通过 `task_id` 关联执行记录，执行记录通过 `plan_id` 关联方案。问题和渠道 ID 仅用于追溯，历史展示以快照为准。

完整的项目资料、方案、问题集合及渠道非敏感配置保存于执行记录的 `plan_snapshot`；逐次结果的 `question_snapshot`、`channel_snapshot` 保留对应问题和渠道配置。执行记录增加 `request_id`（最多 64 个 ASCII 字符，区分大小写）及唯一索引，用于防止同一次创建请求重复建任务；历史记录可为空，新任务由后续创建接口强制提供。API Key、Cookie 和令牌不得进入快照。

已有 011 执行表的数据库执行 `018_diagnosis_exec_request_id.sql` 一次；新库使用最新版 001 或 011，已经包含字段及索引，不再执行 018。2026-10-13 本地 MySQL 已执行 018，执行服务、创建接口及页面已实现，详见 [诊断任务功能与接口](诊断任务功能与接口.md)。

两张表均已配套完整 ORM：`GeoDiagnosisTaskEntity` / `GeoDiagnosisTaskDao`、`GeoDiagnosisTaskResultEntity` / `GeoDiagnosisTaskResultDao`。实体沿用数据库表全名、驼峰字段映射、`IdType.AUTO` 及 Lombok；DAO 使用 `@Mapper` + `BaseMapper`。快照、引用和用量以 JSON 字符串直接读写，不额外包装业务对象或增加 TypeHandler；JSON 格式由 MySQL 校验，内容校验与脱敏由后续创建/执行逻辑负责。创建和更新时间由数据库维护，写入后重新查询回读。

2026-10-13 使用独立 MyBatis-Plus 工厂、显式 JDBC 事务及真实本地 MySQL 验证两个 DAO：增删改查、自增主键回填、JSON 与响应字段、毫秒时间、数据库默认值以及两个唯一键均通过，事务回滚后临时项目、方案、任务及回答无残留。独立工厂验证不代表运行服务已重新加载；本轮未重启服务，未验证 Spring 容器内业务事务或模型执行。

回答正文、接口结构化引用 JSON、实际模型、用量 JSON、耗时、结束原因及原始响应分别保存；未执行时响应字段为空，成功但无引用时保存空数组。原始响应仅保存脱敏后的模型响应体，不得写入请求认证头或凭据。提及、推荐和排名等报告分析字段暂不添加；任务创建、后台执行和结果页面已接入。

一次执行状态为 PENDING、RUNNING、SUCCEEDED、PARTIAL_FAILED、FAILED；单次结果状态为 PENDING、RUNNING、SUCCEEDED、FAILED。整体与渠道统计从结果实时聚合，不重复维护计数字段。唯一键阻止同一次采样重复建记录；第一版不自动重试，失败样本重试后续实现。

列表提供独立的「查看」「编辑」入口。查看弹窗仅展示已保存配置和问题，支持问题分页；创建、编辑保存成功后自动关闭弹窗并刷新列表，保存失败保留输入。

入口：「资产诊断 → 诊断方案」。支持创建、编辑、详情、名称筛选、分页查询及问题生成；保存方案不执行诊断采样，需前往「诊断任务」手动发起。诊断报告后续实现。

主页面保留方案列表，创建和查看／编辑共用居中弹窗。弹窗有遮罩、独立滚动、固定头部和保存区；关闭按钮、Escape 和点击遮罩均可关闭，有未保存内容时在弹窗内提示继续编辑或放弃修改。消息显示在当前弹窗内，背景页面不可操作，关闭后恢复页面滚动。

问题集合使用紧凑行内表格，每页 20 条，支持翻页与直接跳页。翻页保留输入，保存提交完整集合；添加问题或确认候选后定位到新增问题所在页。候选同样以紧凑表格展示供逐项审核。每次生成最多 30 条，可多次追加维护 100 条或更多问题。

## 使用流程

1. 选择基础项目，填写方案名称和每题重复次数。
2. 显式选择被测模型渠道，搜索能力沿用协议配置。
3. 按项目资料生成候选，或添加人工问题。
4. 审核候选的问题、意图、品牌范围和语言，勾选后加入集合；已有人工问题保留，重复文本跳过。
5. 保存方案，预计采样量为问题数 × 渠道数 × 重复次数。

制题模型与被测模型独立。制题未指定渠道时沿用数据库优先级，被测模型必须显式选择。生成失败保留问题与候选；切换项目清除旧候选，保留现有问题供重新审核。异步生成的旧项目结果不会写入新项目。

制题使用全部项目资料；后续真实采样仅发送最终问题，不附加产品资料作为隐藏上下文。

## 表和分层

| 表 | 职责 | 实体 |
|---|---|---|
| geo_diagnosis_plan | 项目、名称、重复次数、时间 | GeoDiagnosisPlanEntity |
| geo_diagnosis_plan_question | 方案独立问题集合和顺序 | GeoDiagnosisPlanQuestionEntity |
| geo_diagnosis_plan_channel | 显式关联被测模型渠道 | GeoDiagnosisPlanChannelEntity |

三张表在同一事务中保存，编辑时锁定方案再替换子集合；项目、渠道使用外键，渠道关联唯一。问题属于方案，不提前建立公共题库或子表转发 Service。

- MgmtDiagnosisPlanController：接口和错误映射。
- DiagnosisPlanBusiness：显式 Request → Entity → Response 转换、列表和生成编排。
- GeoDiagnosisPlanService：关联及问题规则、事务保存、集合查询。
- QuestionGenerateService：通过现有 LLMClient 制题、严格解析，仅返回候选。
- 三个同名 DAO：对应表持久化。

依赖沿用 @Resource，无 BeanUtils 或重复的被动领域模型；原空 QuestionGenerateBusiness 已删除。

## 问题字段与规则

| 字段 | 可选值 |
|---|---|
| source | MANUAL / GENERATED |
| intent | RECOMMENDATION / PROBLEM_SOLVING / COMPARISON / PURCHASE / TECHNICAL / AWARENESS |
| brandScope | NON_BRAND / BRAND / COMPARISON |
| language | 用户指定语言 |
| text | 问题正文 |

意图与品牌范围独立，侧面问题按实际目的标记。非品牌问题不得包含项目名称或别名，忽略全半角、大小写及空白；含品牌的认知和比较问题不能计入自然发现。文本校验不能代替人工审核中立性。

方案名称最多 200 字符，问题 1–200 条、每条最多 2000 字符，语言最多 100 字符，渠道 1–20 个，重复次数 1–10。每次生成 1–30 条。重复文本按全半角、大小写与空白归一化判定。

生成输出必须是完整 JSON 数组，字段、类型、枚举、数量均符合要求；可去除包住整个响应的代码围栏，不猜测或截取任意正文，不吞错为空数组。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | /diagnosis-plans?keyword=&page=0&size=20 | 分页摘要，页码从零开始 |
| GET | /diagnosis-plans/{id} | 完整详情 |
| POST | /diagnosis-plans | 创建，返回 201 |
| PUT | /diagnosis-plans/{id} | 修改 |
| POST | /diagnosis-plans/generate-questions | 候选数组，不落库 |

保存请求包含 name、projectId、repeatCount、channelIds、questions。每个问题包含 text、source、intent、brandScope、language；数组顺序为保存顺序，不接受数据库主键。

生成请求包含 projectId、channelCode（可空）、count、language。输入错误为 400，方案缺失为 404，模型或候选解析失败为 502，错误响应不返回模型原文或凭据。
